# ADR-023 · 回合游标幂等:让「你手里这一局比服务端旧」成为一个有名字的拒绝

- **日期**:2026-09-11
- **状态**:已采纳(五条待裁定项 2026-09-09 Felix 全裁通过;裁定 3 于同日经勘察修订一次,见「裁定 3 的修订经过」)
- **决策者**:Felix

## 背景

`GameController.TurnRequest` 自 Phase 1(`f4b2fb6`)起就带一个 `turn` 字段,前端也自 Phase 1(`78bd5d6`)
起一直在发它——**而服务端从来没读过它**。[工程债 §3.3](../backlog-engineering-debt.md) 早已记下这条
(「`TurnRequest.turn` 服务端从来没读过」),当时是作为数据库幂等那一刀的素材记的。

**没读它会怎样**:一个回合可能在服务端**完整落账**,而客户端**没看到结果**。两条路都真实存在:

| 路径 | 服务端内存 | 服务端盘上 | 客户端 |
|---|---|---|---|
| (a) SSE 写抛(玩家返回 / 切后台 / 网络断)| `engine.turn()` = N+1 | **仍是 N**(`persist` 被跳过)| 停在 N |
| (b) 客户端干净断开,服务端全程成功 | N+1 | N+1 | 停在 N |

路径 (a) 的机制:`SseTurnEventSink.send` 把 `IOException` 转成 `IllegalStateException` 冒泡,
`TurnStateMachine.submitAction` 的 `catch (RuntimeException)` 接住 → 相位放回 `AWAITING_ACTION`、
**`store.persist` 在那之前一行、根本没跑到**。这正是 [ADR-015](ADR-015-overseas-deployment-form-factor.md)
已知代价 5「崩溃回滚一回合是特性非 bug」在断流路径上的延伸。

**然后玩家再点一次,会发生什么**:他手里那一组选项的 id 是上一回合的,而骨架逐字规定
`id 用大写字母 A/B/C/D`(`prompts/event-loop.md`)——**选项 id 跨回合是稳定的**,所以守卫 1
(合法性)**认得它、放行**。于是服务端**又推进了一个回合**。玩家以为自己在重试一个没发生的回合,
实际是走掉了第二个回合,而中间那一回合的叙事他**永远没读到**。

⚠️ **威胁模型不是恶意,是正常使用**:点返回键、切到后台、地铁进隧道、手机锁屏。
四个世界都做得值得反复进出之后(线 C),这条路被走到的频率只会上升。

### 本刀不是什么(逐条,因为每一条都曾被当成「顺手一起做」)

- **不是数据库幂等**。那条(`request_id` 唯一键、跨进程、跨重启)记在
  [工程债 §3.3](../backlog-engineering-debt.md) 的层 2 形态清单里,**今天仍然没做**,本刀一个字都没碰它。
  本刀做的是**同进程内的游标比对**——⚠️ 别让后来者以为幂等已经有了。
- **不是重放**(否决见候选方案 A)。
- **不修内存 N+1 / 盘 N 的偏差**(见「修了什么,没修什么」)。
- **不动 `prompts/` / `golden/` / 引擎 / 校验 / `schemaVersion`(保 "0.4")**。

## 候选方案

### 方案 A:服务端重放上一回合(否决)

服务端缓存上一回合的完整 SSE 帧序列,客户端游标落后时把它重新播一遍——玩家补上他没看到的那一回合。

**否决理由,一条就够**:它**没有可验收判据**。要验证「重放的那一份与当时发出去的那一份一致」,
就得先有一份「当时发出去的」留档去比对,而那份留档本身又要被验证。
**没有可验收判据的机制不建**——这条判据在本轮的 Q1 上已经用过一次,不为本刀降格。
(次要代价:一份逐回合的帧序列缓存,与 `LOG_KEEP=4` 的成本模型正面冲突。)

### 方案 B:服务端读游标 + 落后即拒(本 ADR 采纳)

`turn` 字段已经在 wire 上、已经在发、语义已经确定(服务端回声值)。服务端只是**终于去读它**:
落后 → 409 `turn_stale` → 前端拉一次 `/state` 同步后重渲染。

**为什么这是够的**:玩家真正需要的不是「把那一回合重播给我」,是**「别把我这一次点击当成第二个回合」**
+ **「让我看到现在到底走到哪了」**。第一件由拒绝完成,第二件由 `/state` 完成——而 `/state` 是现成的
(ADR-015 Slice 2),**不新建任何机制**。

### 方案 C:数据库幂等键(`request_id` 唯一键)

层 2 的形态,跨进程跨重启,是这条问题的**完全解**。不在本刀:它要先有数据库。
**与本刀互相指认,不互相替代**。

## 最终决策

### 六条立字(已裁,不得自行调和)

**立字 1 · 比较排在 404 之后、守卫 1 之前。**
两者都是纯读、零副作用、O(1),**排序纯是语义问题不是代价问题**。之所以在守卫 1 之前:

- 游标落后时,守卫 1 是**在一个过期的前提上做判断**——它拿玩家手里那组旧选项去比服务端的新选项集;
- 且 `illegal_action` 那句「无效的行动:X」**把责任指向玩家的选择,而玩家点的是屏幕上真实存在的按钮**。

**先答病因,不先答症状。**
(实测补充:因为选项 id 跨回合稳定为 A/B/C/D,「两条同时命中」本来就罕见——只在模型某回合只给 2-3 个选项、
或一生制世界那个 `X` 出口消失时出现。排序影响的正是这个窄情形。)

**立字 2 · 连相位一起读,消除那个毫秒窗口的误报。**
`engine.apply` 把 turn 推到 N+1 之后、`session.phase().set` 把相位放回之前,有一段窗口——
里面有一次 SSE 网络写和一次文件写,**是毫秒级不是微秒级**。窗口内一次真·并发提交若只比 turn,
会被判成 `turn_stale`,**而准确答案是 `busy`**。

否决「接受误报并写明」的理由:那等于引入一个**只在毫秒窗口发生、无法验收**的分支——
**与方案 A 被否决时用的是同一条判据**。

⚠️ **两次无锁读不构成 [ADR-022](ADR-022-turn-admission-and-rejection-semantics.md) 立字 5 的风险。**
那条禁的是在准入路径上引入**必须永不失败的写操作**(守卫 2 前移会让 CAS 成功后被拒 =
该存档永久 busy)。本刀两处都是**纯读**:`engine.turn()` 与 `session.phase().get()`,不写、不占名额、
不需要归还。两次读之间状态可能变化,但两种交错**都落在相邻两个真值之一**上,没有第三种结果。

**立字 3 · 判 `turn_stale` 的条件 = 相位不在途;在途 = `{GENERATING, SETTLING}`。**
等价说法:**仅当 `AWAITING_ACTION` 或 `ENDED` 才判 `turn_stale`**。

`ENDED` 落在判 stale 那一侧,是本 ADR 最值钱的一条:

> **断流发生在最后一回合,是本刀目标场景里最坏的那一个,而它恰好落在 `ENDED` 上。**
> 玩家在结局那回合断流 → 没看到结局 → 再点 → 今天永远是「上一回合仍在结算,请稍候」,
> **局已经结束了,而他永远出不去。**

⚠️ **这不构成语义重载**:`turn_stale` 只说一件事——**「你手里的游标落后于服务端」**。
在 `ENDED` 上这句话**是真的**(服务端 N+1 且已收束,客户端停在 N),前端据它拉一次 `/state`
就能读到 `status: ended` 与结局,正是玩家要的那个出口。

**立字 4 · 服务端只发 code、不发 message。**
按 [ADR-022](ADR-022-turn-admission-and-rejection-semantics.md) 闸 A 那条规则(**不是特例**):
**状态码本身就能说清的情形,文案归前端兜底表;只有服务端知道的细节,文案归服务端。**
「你的游标落后了」是客户端**自己也知道**的事实(它手里就有那个 turn 值),服务端不掌握任何
额外细节 → 文案归前端。对照 `server_at_capacity`(只有服务端知道此刻挤)与
`illegal_action`(只有服务端知道是哪个动作),两者都自带文案。

**立字 5 · 「在途是哪些相位」的真理源在 `TurnPhase` 上,controller 不许就地枚举。**
新增 `TurnPhase.inFlight()`(纯查询、零副作用,返回 `GENERATING`/`SETTLING` 为真)。

只把 `GENERATING` 换成 `{GENERATING, SETTLING}` 而留在调用点,是**把同一个病换个数字再犯一次**:
今天漏掉第四个值,明天加第五个值时这条判据会**静默失效,没有任何东西会红**。
与「不写聚合数、指登记处」同形——**把一个会随枚举增长而失效的判断,从调用点搬回定义处**。
加第五个值时,作者必须在**一处**做决定,而不是让四个调用点各自漏掉。

⚠️ **它不构成 [ADR-018](ADR-018-base-world-visual-migration-and-severity-contract.md) §4.1 的「两处判定」**:
判定仍然只有 controller 一处,`inFlight()` 只是把**「在途是哪些」这一事实**收归定义处。

⚠️ **这也不是新提法**:`TurnPhase` 枚举自己的 javadoc 逐字就写着
「`GENERATING`/`SETTLING` 期间到来的动作一律拒」。**本刀只是终于按它写的去用它。**
(勘察实证:全 `server/src/main/java` 里对相位的引用**没有一处在枚举在途集合**——
六处全是单值写或两值 CAS,故本刀不需要顺手改任何既有调用点。)

**立字 6 · 修了什么,没修什么。**

- **修了**:挡住「断流之后再点一次 → 服务端推进第二个回合」。
- **⚠️ 一个字都没修**:**内存 N+1 / 盘 N 的偏差**。上表路径 (a) 落地之后,内存里的这一局比盘上新一个回合,
  进程此刻崩溃就回滚一回合(ADR-015 已知代价 5),**本刀不改变这一点**。见「挂账」。
- **也没修**:跨进程 / 跨重启的幂等(那是方案 C)。

### 裁定 3 的修订经过(留档,因为它本身是一条方法论)

裁定 3 最初写作**「仅当 `GENERATING` 才放行」**,而实现前的复查发现 `SETTLING` 才是那个窗口的真实相位
(`EventLoopService` 在主调用结束后、回灌/校验/`apply` 之前就 `phase().set(TurnPhase.SETTLING)`)。
按原措辞落地会让**立字 2 完全落空**——它存在的唯一目的就是消除那个窗口的误报,而那个窗口恰恰是 `SETTLING`。
(同向证据:流中断降级那条路在 `SETTLING` 被设置**之前**就 `applyNoOp` 推进了 turn,
所以 **turn 被推进的那一刻,相位可能是两者中的任何一个**。)

⚠️ 而这个错误的来源是上一轮的勘察报告:它写了「其间相位恒为 `GENERATING`」,裁定据此作出,
**而那一轮验的是别的东西,没验这一条**。定性:**验产物时选错了对象——挑的是「读起来可疑」的那个,
不是「在承重」的那个。** 归 [ADR-018 §4.14](ADR-018-base-world-visual-migration-and-severity-contract.md) 那一族。

修订后**载荷一字未变**(ENDED 仍判 stale,那句最值钱的话原样成立),变的只是放行侧的枚举——
而立字 5 的存在,正是为了让下一次这种遗漏**会红**。

## 关键理由

**拒绝形态为什么不丢内容**(玩家不会因为这个 409 而失去那一回合):

- 前端收到 `turn_stale` 后拉一次 `GET /api/game/{saveId}/state`;
- 该端点走 `GameInitService.resume`,读的是**内存现值**(`session.engine().toClientState()` +
  `session.currentActions()`),**不读盘**——所以即便盘上还是 N,玩家拿到的也是 N+1;
- 而 `Engine.snapshot()` 的 `state.log` 取的是**末 `LOG_KEEP = 4` 条**,
  **断流那一回合的 narrative 仍然在里面**(前端续局散文补位读的就是 log 末条)。

**所以这个拒绝是「让你看到你错过的那一回合」,不是「把它扔了」。**

## 已知代价

1. **`/state` 在一个极窄的子窗口里不自洽。**`engine.apply` 之后、`updateActionsFromParsed` 之前
   (中间只有日志、无 I/O),`/state` 会返回**新回合号 + 新叙事 + 旧选项文案**。
   因 id 稳定为 A/B/C/D,**不一致的是选项文案不是 id**,玩家点下去仍然合法。
   ⚠️ 如实记:它确实存在,本刀不修(修它要把 `apply` 与 `updateActions` 合成一个原子步骤,
   那是动引擎结算序列,代价与收益不成比例)。
2. **两次无锁读的交错**:见立字 2 —— 结果落在相邻两个真值之一,没有第三种,不修。
3. **`ENDED` 上的行为变化是永久的,不是竞态**:整局结束后,落后客户端的重复点击从
   `busy` 变成 `turn_stale`。这是裁定 3 要的,但它意味着**每一次**都变,不是偶尔。
4. **同进程内有效,进程外无效**:重启后内存表由 `reloadFromStore` 回载,`engine.turn()` 取自盘上那份
   (路径 (a) 下就是 N)——此时客户端的 N 与服务端的 N **相等**,比较放行,回合会被推进。
   ⚠️ **这不是 bug,是本刀边界的诚实位置**:那正是方案 C(跨重启幂等键)存在的理由。

## 挂账

### 内存 N+1 / 盘 N 的偏差(Q3,本刀明确不治)

断流路径 (a) 下,内存里的这一局比盘上新一个回合,且**没有任何东西会把它们对齐**——
下一个成功回合的 `persist` 会写入 N+2,盘上从此少了 N+1 那一回合的中间态。
玩家侧后果:此刻进程崩溃 / redeploy,他会回滚到 N(ADR-015 已知代价 5 的既有语义)。

**不治的理由**:治它要么在异常路径上也 `persist`(而那条路径上 `sink` 已经在抛,
写盘成功与否无人可报),要么引入一个对账机制——两者都比本刀大,且**都不改变玩家可见行为**
(玩家看到的是 `/state` 的内存现值)。**解冻条件**:方案 C(数据库)开工时一并解决,
届时「内存」与「盘」不再是两份东西。

### 客户端**不落后**而局已结束时仍拿 `busy`(与本刀无关,故不进本刀)

`TurnStateMachine` 守卫 2 的注释逐字自己就写着「CAS 失败 = 该回合正被处理**或整局已结束**」,
而它发出去的文案照旧是「上一回合仍在结算,请稍候」。**游标不落后 + 局已 ENDED** 的那一次点击
(第二个页签同步刷新过、或结局帧收到后又点了一下)今天拿到的就是这句不准的话,
**本刀改不到它**(它压根不落后,比较会放行)。

⚠️ **与 turn 无关,是守卫 2 自己的文案账**,单独记,不夹带进本刀。

## 重新审视的触发条件

- **方案 C 开工时**(数据库 + `request_id` 唯一键):本刀的游标比对是否保留、还是被幂等键取代,须重估。
- **`TurnPhase` 增加第五个值时**:必须在 `inFlight()` 一处做决定——立字 5 就是为这一刻写的。
- **回合改成可中断 / 可取消时**:「在途」的定义会变,立字 3 随之重估。
- **`/state` 变成读盘而非读内存时**:「拒绝不丢内容」那条论证的前提就没了。

## 测试面

五条用例,五次变异各自变红(缺一条就说明那条守护在守空气):

| # | 用例 | 变异 |
|---|---|---|
| (a) | 游标落后 + 相位 `AWAITING_ACTION` → 409 `turn_stale` | 摘掉比较 |
| (b) | 游标相等 → 正常推进(提交一次) | 比较写反 |
| (c) | 比较方向错(`>` / `<` 互换)必须有用例红 | 改方向 |
| (d) | **窗口内(`SETTLING`)落后提交 → `busy` 不是 `turn_stale`** | `inFlight()` 只返回 `GENERATING` |
| (e) | `GENERATING` 期间落后提交 → `busy`(降级那条路) | 同上 |

⚠️ **(c) 的硬前提**:至少一个用例的 `engine.turn()` **不为 0**。
现有夹具十二处全传 `TurnRequest(0, …)`,而新起 session 的 `engine.turn()` **也是 0**——
**`0 == 0` 让任何写法都绿**。用 `Engine.applyNoOp`(public,首行 `turn += 1`,不需要 LLM、不需要 mock provider)
把它推到 1。
⚠️ 另加一条 `ENDED` 用例(立字 3):局已结束 + 客户端落后 → `turn_stale`,**不是** `busy`。
