# ADR-018 · 基础世界视觉移植:severity 语义契约 + 单一主题注册表 + 四刀切分

- **日期**:2026-07-24
- **状态**:已采纳
- **决策者**:Felix

## 背景

[ADR-017](ADR-017-frontend-visual-charter-and-animation-libraries.md) 立了视觉宪法、白名单三库与第一版范围,并把执行形态**两段分开**:探索走 Cowork 独立视觉样板间(不直接改 `web/src`),落地回 Claude Code 流程(feature 分支 + 测试 + 冒烟)。探索段已完成——样板间 `~/code/wanjie-visual-lab` 的四世界视觉语言、动效编排与记忆点方案**已验收冻结**,移植勘察已完成,八个待决问题已全部裁定。

本 ADR 是**落地段的总纲**:它不重复样板间的视觉设计(那是被冻结的成果),而是回答「把冻结的成果搬进生产,架构上要立哪些字」。

### 移植不是复制粘贴

样板间与生产是两种东西,四条结构性差异决定了移植必须重写接线而非搬运文件:

| | 样板间(冻结成果) | 生产 `web/` |
|---|---|---|
| 数据 | 写死的示例数值与文案 | AI 实时生成,数值每回合变、文案不可预测 |
| 组织 | 六个彼此独立的演示屏 | **一套组件切皮肤**(`GameScreen`/`StatsPanel`/`Prose`/… 四世界共用) |
| 轴 | 硬编码轴名(「气血」「理智」写死在 JSX) | **轴语义无知**(ADR-008:按 init 下发的 `attributes` 元数据遍历渲染,加世界不改组件) |
| 世界数 | 四个基础世界 | 四基础 + **两个融合局**(识海遗蜕 / 缺页的人防工程),融合局的轴带换皮(道心 / 补给) |

样板间可以写「气血低于 20 就变红」;生产不可以——生产的组件在运行时**不知道自己在渲染哪个世界的哪根轴**,也不该知道。这条约束不是本 ADR 新加的,它是 ADR-008 立的引擎/展示层数值无知在视觉层的必然延伸。于是问题变成:**危险感这种语义,谁来产出。**

### 触发本 ADR 的具体缺口

样板间四世界的数值组件都有「危险态」表现(规则怪谈的血色渗出、修仙的气血枯竭、克苏鲁的深陷、末日的濒临饿毙)。要在生产复现,渲染方必须知道「当前这一档危不危险」。而生产的 `StatsPanel` 今天拿到的 `bands` 只有 `{min, max, label}`——`label` 是给人读的中文短词(「濒危」「深陷」「灵力枯竭」),**不是给机器判的语义**。前端要么按 label 文本猜(脆、一改文案就错)、要么按 key 硬编码(违 ADR-008)、要么按数组位置猜(下一节说明为何这也是错的)。

## 候选方案

### 方案 A:前端自己判断危险(按 key 硬编码 / 按 label 文本匹配 / 按位置启发)

前端维护一张「哪些 key 是生命轴、哪个位置的 band 危险」的表。

**优点**:
- 后端零改动,刀 0 可以直接跳过。

**缺点**:
- **违 ADR-008 引擎/展示层数值无知**:每加一个世界或一根轴,前端要跟着改表——正是 ADR-008 花大力气消除的代价结构;
- 融合世界直接失效:道心(`san` 换皮)、补给(`hunger` 换皮)在前端看是同一个 key,但换皮后的 `bands` 文案与 host 世界观绑定,label 匹配必错;
- 按位置猜更错:轴的档数不保证是 3,且 `bands` 在 registry 里的**存储顺序是降序**(depletion 写作 100/50/20),下标语义完全不可靠;
- 「这个数值危不危险」是**世界设计语义**,前端手里没有做出该判断所需的信息(`axisRole`/`lethal`/是否双刃全在服务端元数据里,且刻意不下发)。

**排除**:让消费方猜生产方才知道的事,是本项目已经三次拒绝过的做法。

### 方案 B:服务端派生 severity,前端只渲染(本 ADR 采纳)

`axesJson` 的每个 band 增一个 `severity: "neutral" | "caution" | "danger"`,由服务端据轴元数据(`axisRole` / `lethal` / 新增 `perilAtHigh`)派生。前端只做**数据匹配**(`min ≤ value ≤ max` 找当前档)与**渲染**(按 severity 决定视觉状态),不做任何语义判断。

**优点**:
- 语义在掌握语义的那一层产出,与 ADR-010 / ADR-011 同构(见「关键理由」);
- 融合世界零登记自动正确:`AxisSkin` 只换 `displayName`/`bands`/`behaviorHint`,不换 `axisRole`/`lethal`/`perilAtHigh` → 道心与补给自动继承 host 侧的正确 severity,加组合不为此做任何事(守 F-016 成本模型);
- 前端四套皮肤只呈现风险等级,加世界 = 后端加一条元数据,前端零改。

**缺点**:
- 多一个展示层元数据字段(`perilAtHigh`),元数据面继续变厚。

**采纳**:缺点是一个字段,优点是把「危险感」从四套皮肤里各判一次收敛成服务端派生一次。

### 方案 C:服务端直接下发视觉指令(颜色 / class 名 / 动画参数)

**优点**:
- 前端最薄。

**缺点**:
- 把展示层决策搬进后端,违 ADR-003「展示层语义无关」的反向——后端开始关心红色和闪烁;
- 每次调色板微调都要改后端并重新部署;
- 四世界视觉语言不同(同为 danger,规则怪谈是血色渗出、克苏鲁是孢子扭曲),下发颜色等于把每世界视觉语言表也搬进后端。

**排除**:severity 是**风险等级**,不是**视觉表现**。下发前者、不下发后者,是这条线的正确切法。

## 最终决策

### 1. 语义产出方原则(本 ADR 的核心立字)

> **语义由掌握语义的那一层产出,消费方一律无知。**

推论(逐字锁,后续视觉工作一律援引):

- 前端根据明确区间匹配当前 band(`min ≤ value ≤ max`)= **数据匹配,合法**;
- 前端判断这个 band 危不危险 = **语义判断,必须在服务端完成**;
- 四套数值组件**只呈现风险等级,不猜测数值好坏**。任何主题组件不得重新解释轴语义。

这是该原则第三次实例化:

| ADR | 语义 | 产出方 | 消费方 |
|-----|------|--------|--------|
| [ADR-010](ADR-010-ending-outcome-polarity-gate.md) | 结局极性 `outcome` | AI 标注 | 引擎只读、不解读结局语义 |
| [ADR-011](ADR-011-action-hint-narrative-metadata.md) | 选项风险提示 `hint` | AI 写 | 引擎只读透传、永不 gate/掷骰 |
| **ADR-018** | 数值风险等级 `severity` | **服务端派生** | **前端只渲染** |

三次的形状一致:产出方是唯一掌握该语义的层,消费方拿到结论就用、不复算、不反推、缺失就安全降级。

### 2. severity 契约(刀 0 的全部范围)

**2.1 wire 形态**

`InitResponse.attributes[].bands[]` 每项由 `{min, max, label}` 增为 `{min, max, label, severity}`,`severity ∈ {"neutral", "caution", "danger"}`。

- **不改 world JSON、不改 prompt、不改 turn delta**;
- `schemaVersion` 保 **"0.4"**——`bands` 一族走 **API DTO**(`InitResponse`),非被校验的 wire schema(同 #3 数值行为化落 `bands` 时的口径,CONTEXT §三.14);
- **init 与 resume 走同一构建路径**(现状即 `GameInitService.attributeMeta(List<AttributeAxis>)` 唯一构建点,两处共用;本 ADR 把它由现状升为约束)。

**2.2 判别位:`perilAtHigh`(第四个展示层轴元数据)**

`AttributeAxis` 增 `perilAtHigh`(布尔,默认 `false`)。

**定位写死**:`perilAtHigh` 是**纯展示层元数据**——**引擎/校验绝不读它**,不进 JSON schema、不进 wire schema、`schemaVersion` 保 "0.4"。它与 `bands`/`behaviorHint` 同族(伴生结构,非 state schema 字段)。

**血统**(per-archetype 轻量元数据的第四次扩充):

| ADR | 加的字段 | 引擎读不读 |
|-----|---------|-----------|
| [ADR-008](ADR-008-multi-mode-extension-architecture.md) | 立 per-archetype 轻量元数据 + 引擎数值无知;`behaviorHint` | 不读 |
| [ADR-009](ADR-009-axis-roles-and-rule-form-flexibility.md) | `axisRole` | **读**(引擎唯一会读的轴语义,触底二分) |
| [ADR-010](ADR-010-ending-outcome-polarity-gate.md) | `lethal` | **读**(致命轴触底 + 结局极性 gate) |
| [ADR-014](ADR-014-fusion-skeleton-parameterization-and-second-combo.md) | `AxisSkin.behaviorHint` override | 不读 |
| **ADR-018** | **`perilAtHigh`** | **不读** |

**为什么需要它(如实记)**:原 brief 给的派生规则(「lethal accumulation 最高档 danger」)与验收 ②(「禁忌知识高位 danger」)**自相矛盾**——禁忌知识是 accumulation 但 `lethal=false`(`AttributeAxis.accumulating()` 硬写,CONTEXT §三.14 亦立字「accumulation 轴恒 `lethal=false`」),按原规则应全 neutral。仓库里**不存在 lethal accumulation 轴**,且 `lethal` 是引擎会读的字段(改它会改触底与结局 gate 行为)——**绝不能为了染色去动它**。矛盾出在 brief;实现前停下报告是正确处理。

今天能区分「禁忌知识越高越危」(双刃)与「境界越高越好」(纯成长)的,只有 `behaviorHint` 里的中文散文,不可机读。`perilAtHigh` 就是把这个已经存在的世界设计事实变成机器可读的一位:

- `knowledge`(禁忌知识)`perilAtHigh = true`——累积型双刃,越高越接近疯狂;
- `realm`(境界)`perilAtHigh = false`——纯成长,越高越强。

两者同为 accumulation 却结果相反,**正是该字段存在的理由**。

**2.3 派生规则(四分支)**

| 轴 | severity |
|----|----------|
| 非致命 depletion(灵力) | 全 `neutral` |
| 致命 depletion(体力/理智/饥饿/气血/道心/补给) | 最低档 `danger`、次低档 `caution`、其余 `neutral` |
| accumulation 且 `perilAtHigh`(禁忌知识) | 最高档 `danger`、次高档 `caution`、其余 `neutral` |
| 其余 accumulation(境界) | 全 `neutral` |

**实现约束(逐字锁)**:

- **不得按数组下标写死「第二低 / 第二高」**——registry 里 `bands` 的存储顺序是降序(depletion 写作 100/50/20),下标语义不可靠。**先按 `min` 排序**(即挂在已排序的 `bandRanges()` 输出上)**再据轴角色标记边缘档**及其相邻档;
- 档数 `< 2` 时**只标边缘档、不报错**(退化情形合法);
- `bands` 异常(重叠 / 留空 / 无序 / 越界 / label 空)**在后端测试直接失败**——现状已由 `AttributeAxis` 构造器 `validateBands` 保证(registry 配错档 = 类加载即抛,上不了线),本 ADR 把它升为显式验收项。**绝不下发一份让前端猜的区间表**。

**2.4 融合世界:per-combo 对 severity 零登记**

`AxisSkin`(ADR-012 决策 2 / ADR-014 决策 4)**不得换 `perilAtHigh`**——它与 `key`/`axisRole`/`lethal`/`min`/`max` 同属「换皮不换」的清单。换皮只换 `displayName`/`bands`/`behaviorHint`。

因此融合局的 severity **自动等同于对应 host 侧单体**,新增融合组合**不为 severity 做任何事**(守 [F-016](../../bakeoff/FINDINGS.md) 立的复用成本模型:加一对组合 = 后端 5 处纯文案 + 前端 3 条登记,不因视觉再加一处)。

**2.5 前端缺省行为(一律安全降级)**

四种缺省情形——**无 `bands`** / **值找不到所属 band** / **老数据无 `severity`** / **未知 `severity` 值**——统一表现为:

> 数字与 label 正常显示,**不附加危险色、不进入警告态**。

**绝不默认 `danger`,绝不回退旧启发式**(不按 key 猜、不按 label 文本猜、不按位置猜)。降级方向恒为「安静」——把不确定渲染成危险,等于给玩家一个假的状态播报。

### 3. 四刀切分

| 刀 | 范围 | 状态 |
|----|------|------|
| **刀 0** | severity 契约(后端派生 + TS 类型与兼容解析) | 本工作单元 |
| **刀 1** | 共享基建 + 规则怪谈试验田 | 另起 |
| **刀 2** | 修仙(含钟鸣记忆点) | 另起 |
| **刀 3** | 末日 | 另起 |
| **刀 4** | 克苏鲁(含文字异常记忆点) | 另起 |

**刀 0 · severity 前置**
做:后端 severity 派生(init/resume 同一路径)+ 前端 TS 类型与兼容解析。
**不准顺手做**:不上任何新皮肤、不改任何组件渲染、不装任何 npm 依赖、不碰 `game.module.css` 的视觉、不动 `StatsPanel.barClass` 与 `ArchetypeSelect.vibeClass`(它们归刀 1 收编)。

**刀 1 · 共享基建 + 规则怪谈试验田**
做:主题注册表、数值组件通用层/主题层分工、动效令牌(`--t-dur`/`--t-ease`)、生命周期 teardown、feature gate,**只有规则怪谈登记新主题**。
**不准顺手做**:不顺手把另外三个世界一起登记(试验田的意义是先证明基建,四世界一起上等于没有试验田);不做记忆点(记忆点跟着各自世界的刀走);不改后端。

**刀 2 · 修仙**
做:修仙主题登记 + 一级记忆点「一声钟鸣」(ADR-017 §6.3 订正后口径)。
**不准顺手做**:不动共享基建的结构(基建缺口应回头改刀 1 的产物、不在主题层打补丁);不给别的世界加记忆点。

**刀 3 · 末日**
做:末日主题登记 + 电台内容池。
**不准顺手做**:不做「饥饿」轴改名(已在 [打磨与愿景 backlog §6](../phase2-polish-and-vision-backlog.md) 独立挂账,涉及 prompt/condition 文案,不属视觉刀)。

**验证目标重述(Felix 2026-07-27 修正自己的上一条口径)**:刀 3 原本被期望为「共享基建一行不改」。**该期望作为期望是对的,当硬约束是错的** —— 刀 3 勘察用一个真实构图需求把它证伪了:末日的电台是**内容流里的独立区块**(位置在正文与决策之间),而 `WorldSkin` 只有 Ambient / Stats / Actions 三槽,**没有这个位置**。

于是刀 3 的验证目标改述为:**「基建的抽象是否够用」,而不是「一行不改」**。

- **真实需求超出三槽 → 契约小幅扩展(加一个可选槽)→ 其余一律不动 = 抽象正常演化**;
- 为守「零改动」把电台硬塞进 Stats(**一个槽承两种语义**)才是**抽象腐坏** —— 那种「零改动」是假的,它把成本从契约挪进了组件内部,下一个刀会更难。

为什么电台必须在正文**之后**(不是 A/B 两个零改动方案):电台是「读故事时背景里那台机器响了一下」——**读完情境 → 电台响 → 做决定**,那一下响是决策前的最后一个扰动;放到正文之前改的不只是位置,是**叙事节奏**;放到页面顶部则让它变成 UI 条,失去「废土上那台收音机」的物理感。

新槽刻意做成**通用可选内容槽**而非「末日电台槽」:刀 4 克苏鲁的 Prose 重写、C 批叙事壳层差异化都在这一带,**现在立一个干净的可选槽,好过以后挤压现有三槽**。不配置该槽的世界一律不渲染 —— 刀 1/2 产物与其测试零影响。

**刀 4 · 克苏鲁**
做:克苏鲁主题登记 + 一级记忆点「文字异常」(含形近字表,见 §4 Q3)。
**收口须复查**:异常调度器若持锁,按 **§4.11** 补独立于 rAF 的兜底放锁(刀 3 在这里踩过)。
**不准顺手做**:不做 AI 标注异常字方案(依赖尚不存在的 structured narrative schema,已挂 [future-experience-backlog](../future-experience-backlog.md));不因形近字不够而降质替换成任意字。

### 4. 刀 1 的结构性要求(ADR 立字,实现留后续工作单元)

**4.1 单一主题注册表**

**世界判定只发生一次**,子组件消费判定结果,**不得各自再判 archetype**。

收编现有两处私有分派:

- `web/src/features/game/scene.ts` 的封面分派(已有测试与缺图降级,形态正确,收编即可);
- `web/src/features/game/ArchetypeSelect.tsx` 的私有 `vibeClass`(**无测试、无降级**,一并提升到注册表并补上两者)。

**4.2 数值组件职责边界**

- **通用层**:遍历 axes / 匹配 band / 取 severity / 输出可访问文本;
- **主题层**:只决定形态与视觉状态。

**任何主题组件不得重新解释轴语义**(不得读 key 判断这是什么轴、不得读 label 判断危不危险)。

**4.2.1 数值显示的单一驱动量(刀 1 冒烟后补,Felix 2026-07-24 裁定)**

数值滚动期间,**数字、行为档档名、severity 状态灯必须由同一个 `displayValue` 驱动** —— 数字滚过阈值的那一帧同步翻档。

禁止三种写法:

- 开始滚动就套用**目标** severity(数字还没到,警告先到);
- 数字滚完再**延迟补**状态(状态迟到);
- **每个主题各做一套同步规则**(四个世界四种口径,且每套都要重验一遍)。

**同步逻辑必须落在共享 `StatsPanel` 的动画值上,不进主题层**(通用层职责,§4.2)。皮肤只提供**时间感**(滚动时长与缓动),不碰同步。`prefers-reduced-motion` 下不插值,三者同帧直接切换。

**4.3 动效令牌 `--t-dur` 与 `--t-ease` 成对落地**

只换时长不换缓动 = 四世界只是**快慢不同**,不是**时间感不同**——那不叫每世界有自己的视觉语言。两者必须成对,并含 `prefers-reduced-motion` 覆盖值。

**4.4 生命周期:同一个 teardown**

组件 unmount / 主题切换 / turn 切换**必须走同一个 teardown 函数**,不得出现三套近似清理逻辑(三套近似逻辑 = 三处各自漏一点,且漏在最难复现的路径上)。

- `generating` 与 reveal 打字期,低频调度**停表**(正文是禁区,AGENTS.md Motion Constraints §5);
- 测试环境补 `matchMedia` polyfill(jsdom 不带,同 Slice 2 补 `localStorage` polyfill 的先例)。

**4.5 feature gate**

刀 1 后**只有规则怪谈登记新主题**,其余世界走旧实现。出问题**删一条注册即回退**,不得要求回滚整套基建。

**4.5.1 「其余世界 DOM 不变」是等式,不是印象 —— 刀 2/3/4 的标准验收手段(刀 1 已用)**

每刀只登记自己那一个世界,故每刀都必须证明**未登记世界的产出逐字节不变**。方法固定下来,后续刀照做:

1. `git worktree add <tmp> origin/main`,在该 worktree 起第二个 dev server(不同端口),软链 `node_modules` 复用;
2. 两个 dev 喂**同一份数据**(同一桩后端 / 同一续局 saveId);
3. 对每个未登记世界的游戏屏与选择屏,取 `<main>` 子树 outerHTML,**归一化 CSS Modules 哈希**(`_name_hash_n → name`)、折叠空白与打字进度,算长度 + 校验和;
4. **两边必须完全相等**。

刀 1 首轮对拍差 2 字符(模板串拼 class 的尾随空格),已改为数组 `filter(Boolean).join(' ')` 消除 —— **「除空格外不变」不算通过,必须是等式**。(这也顺带守住:主题 token/皮肤挂载不得给未登记世界的 DOM 添任何属性。)

**4.5.2 纯 CSS / 纯样式批次:对拍法本身会失去正对照(修仙屏视觉收敛批立字,2026-07-31)**

刀 2–4 每刀都改了某个世界的 DOM,于是「**该世界两边不等**」天然充当**正对照** —— 它证明两个 dev 确实是两个不同构建,四处全等才有意义(刀 2 的 `3702 vs 2043` 正是这个作用)。

**纯 CSS / 纯样式批次没有这个正对照**:修仙屏视觉收敛批改的是色板 token、卡片透明度、边框与留白,外加一个静止时不挂的条件 class —— **连被改的那个世界 DOM 也逐字节不变**。此时「四处全等」与「我拿同一个构建自比了两次」**在读数上完全无法区分**,而后者恰恰是最容易发生的操作失误(端口写错、worktree 没起来、HMR 指向同一份源码)。

> **补充条款:纯 CSS / 纯样式批次必须另行证明两个构建确实不同,不得只凭 DOM 全等宣告通过。**

可用的证明形式(任一,取**本批真正改动过的**那个量):

- **计算样式取值差异**:同一元素同一属性两边取值不同(本批实测 `--bg` `#d6dfe1` vs `#e7ede9`、正文卡 `border-top-width` `0px` vs `1px`、`padding-top` `21.6px` vs `16px`);
- **变量声明者差异**:遍历 `document.styleSheets` 找出声明某 token 的选择器集合,两边不同(本批 `--prose-*` 的声明者 HEAD = `[.prose, .screen(修仙)]`、BASE = `[]`)。

**顺带**:本批动了共享 `game.module.css`(给 `.prose` 抽了四个带 fallback 的 token),故除 DOM 对拍外还须证明**未登记世界的计算样式**不变 —— 实测规则怪谈 `.prose` 两边同为
`rgba(20,28,34,0.82) | 1px | … | none | 16px | 16.8px | 16px | 16.8px | 2px`。**共享 CSS 被触碰时,DOM 全等不足以说明问题,计算样式才是**。

这与 **§4.13(守护测试可能假绿)**、**§4.14(观测工具本身需要被验证)同族**:三者都是「**验证方法本身失效**」——绿 / 全等有两种解释(东西是对的 / 这个方法此刻测不出东西),而读数本身**不区分这两者**,必须由另一个独立读数把它们分开。

> **补充(ADR-021 刀 1 立字,2026-08-15):纯重构刀次须另造阳性对照,不得依赖被测改动本身。**
>
> 本条原文针对的是「纯 CSS 批次」,但根因与 CSS 无关 —— **凡是「改动本身以不产生任何输出差异为验收标准」的刀次,都没有天然正对照**。ADR-021 刀 1(把三条族级原则从世界层提到族层)是**后端纯重构**的同一形态:全部七个世界的 prompt 逐字节不变**是目标而不是副作用**,连被改的《寻常》自己也全等 —— 于是「全等」与「我 dump 了同一个构建两次」读数完全一致。
>
> **阳性对照必须由「故意插入的改动」造出来,且要能分辨两件不同的事**:(a) **管道通不通** —— 在**共享层**(骨架)插哨兵,期望**全部**产物变;(b) **新抽象接没接上、且对非成员是否真的无害** —— 在**新抽出的那一层**插哨兵,期望**只有成员**变、非成员逐字节不动。刀 1 实测:骨架哨兵 **14/14 变**;族层哨兵 **只有《寻常》2 处变、其余 12 处不变**。
>
> **只做 (b) 不够**(证明不了 dump 读的是新构建),**只做 (a) 也不够**(证明不了新层接进了谁)。而「用两次独立编译证明构建不同」这条路**只能答 (a) 的一半** —— 它证明两个构建确实不同,**证明不了新抽象通到了哪些世界**。

> **另附(同刀实测,§4.14 的又一次兑现):观测工具本身先出了两次错,而两次都表现为「代码回归」。**
> 刀 1 首轮对拍报出 **6/14 DIFF**,逐条 diff 后两个真因**全在 dump 工具里**:① harness 用 `Map.of` 装数值轴,而 **`Map.of` 的迭代顺序每个 JVM 实例都不同** → `attributes` 的 key 序在两次 dump 间随机变化;② world-gen prompt 尾部**按设计随机挑场景种子**(F-005 多样性),两次必然不同。修工具(定序 `LinkedHashMap` + 裁掉随机种子后缀)后才拿到真读数 **14/14 IDENTICAL**。
> **教训与 §4.14 同形但方向相反**:那条说探针会**漏报**(撒谎说没事),这条说探针会**误报** —— 而误报同样危险,因为下一步很自然就是「回去改代码」,去修一个根本不存在的回归。

> **世界决定明暗:游戏屏不跟随系统浅/深色偏好。每个世界主题自带完整色板,主题根覆盖 + 铺底层盖满视口。未登记世界仍跟随系统偏好(旧实现不变)。**

**4.7 一级记忆点与开场叙事**串行**(刀 1 冒烟后订正,Felix 2026-07-24)**

> 顺序:**场景进入 → 短暂稳定 → 记忆点 → 余韵(数十至数百 ms)→ 正文开始逐字**。

**这是对同日早些时候「入场即放、与打字重叠」裁定的推翻**,理由记明:

- 串行**没有**破坏「进门那一下」的语义,**反而更对** —— 先看见环境,再进入叙事;
- 彻底消除记忆点与阅读抢注意力的风险(视觉宪法第一条是唯一一票否决项);
- 原先反对串行的理由是「多一条打字完成信号的跨组件耦合」,**这个小代价值得付**。

实现约束:通用层持有放行闸(`hasIntro` + `onIntroDone`),皮肤被抑制(reduced-motion / 生成中)时**必须立即回调**;通用层另设**兜底计时器**,皮肤没回调也要放行 —— **叙事永远不该被动画卡住**,兜底是保险不是设计路径。

**4.8 承载表面必须先验证「能不能被看见」(刀 1 冒烟教训)**

刀 1 第一版把压暗层放在内容之下以保证「正文不受影响」。实测(375×812):顶部场景图处透过率 **0**、OSD 面板 0.12、正文面板 0.18,**全屏平均 0.201,只有 13% 面积真的在暗**,且那 13% 是黑底上的细缝。

**「正文绝对不受影响」与「整屏可感」在同一层叠顺序里无解** —— 这不是强度不够,是方案自相矛盾。**解法是换承载表面,不是加强度**:

- 记忆点应作用在**该世界视觉上最大、最不透明、最先进入视线的那个面**(规则怪谈 = 顶部场景图,它就是那个房间)+ 氛围层;
- 正文与选项**不加滤镜、不改 opacity**,阅读绝对稳定;
- 提案任何新记忆点时,先回答**「它作用在哪个面、那个面占屏多少、会被什么遮住」**。

**4.9 一次性效果的守卫记「已开演」,不记「已排期」(同批教训)**

React StrictMode(开发模式)会走 挂载 → 清理 → 再挂载;中间那次清理会 `teardown()` 掉已排期的定时器。若守卫记的是「排过期了」,第二次挂载直接跳过 —— **本地开发下入场序列永远不会播**(这正是刀 1 冒烟「无法确定灯闪是否发生」的第二个真因,与遮挡各占一半)。

守卫必须记**有没有真的开演**:重挂载会重新排期,而换回合不会(effect 依赖里没有 turn)。该失败模式已有回归测试钉住(用真实接线 `useSkinRuntime` + StrictMode,手动 new 一个 runtime 是复现不出来的)。

**4.10 形态与阴影必须同源(刀 2.5 教训,提前给刀 3/4 立字)**

> **`box-shadow` 画的永远是矩形(或 `border-radius` 后的圆角矩形),只有 `filter: drop-shadow()` 跟随 `clip-path` 之后的实际轮廓。**

刀 2.5 的境界印是 `clip-path` 切出来的八边玉印,钟鸣要「沿印的轮廓先亮一圈」。若照直觉用 `box-shadow` 发光,元素会长出一圈**矩形辉光**罩在八角形外面 —— **形态当场破功**:玩家看到的不再是一方玉印,而是一个被剪成八角的方块。同理,`box-shadow: inset` 描的内圈也是矩形边,在斜切的边上会断掉。

适用面不止本刀:**刀 3 末日的磨损切角、刀 4 克苏鲁的撕裂底边**都会用非矩形轮廓,一律遵守 ——

- 轮廓光 / 外发光 → `filter: drop-shadow(...)`(跟形状);
- 需要「描边」时,不要用 `border`(`clip-path` 会把它切掉),改**外层染色 + 内层内切**露出一线边;
- 只有当元素确实是矩形/圆角矩形时,`box-shadow` 才是对的(灵脉的圆角柱、卡片辉光仍用它)。

判据一句话:**问「这个光该跟着谁的形状」,答案是 clip 后的形状就用 drop-shadow**。

**4.11 「周期性调度 + 生命周期清理」的沉默失效(一族,两种子模式;刀 3 取证 + 刀 4 扩写)**

> **凡「周期性调度 + 生命周期清理」的组合,必须验证:清理之后**有人负责重新开始**。**

本节最初(刀 3)只记了子模式 A(锁被永久占住)。刀 4 又撞到子模式 B —— 机制完全不同(与锁无关),但**失效表象一模一样**:无报错、无崩溃、无日志,只是「那个效果再也不出现了」。故升为一族,两例并列。

**共同特征(这才是要记住的东西)**:两者都不是「功能写错了」,而是**「谁在什么时候把它重新启动」这个问题没有答案**。这类缺陷几乎不可能被功能冒烟发现 —— 玩家只会觉得「今天电台好像没响过」,而开发者复现时往往停在第一回合。**唯一可靠的抓法是时序探针读数 + 跨生命周期的守护测试**。

---

**子模式 A · 异步锁 + 可冻结时钟(刀 3 冒烟取证)**

> **任何持锁的异步效果,必须有一条独立于 rAF 的兜底放锁路径。**

刀 3 的远光与电台**互斥共用一个低频槽**(§2.1),互斥靠 `runtime` 忙态锁。远光原本只在 GSAP `onComplete` 里放锁 —— 而**页面转入后台时 rAF 冻结、GSAP timeline 永不完成**,锁就被永久占住,**与它共槽的电台从此静默**,直到换回合 teardown 才恢复。

这个失效模式的特征值得记住:**无报错、无崩溃、无异常日志** —— 表现只是「那个效果再也不出现了」,而这恰恰是最难在冒烟里被发现的一类(玩家只会觉得「今天电台好像没响过」)。刀 3 是靠**时序探针读数**抓到的:`fired 16316ms` 之后 `completed` 一直是 `—`。

三条推论:

- 调度侧的 `!document.hidden` 只能防「**隐藏时开演**」,防不住「**开演后被隐藏**」——两者都要防;
- 兜底必须用 **`setTimeout` 而不是 rAF/GSAP**:计时器在后台仍会跑(只是被钳到 ≥1s),而 rAF 是真的停;
- 放锁做成**幂等**(正常收尾与兜底谁先到都行,第二次是 no-op),否则会出现「兜底放了锁、真收尾又放一次」的重入。

**刀 4 复查结果**:克苏鲁的文字异常调度器同样持锁(一次事件最长含 12s 标点余韵),已挂 16s 的 `setTimeout` 兜底放锁、幂等。**顺带在这里踩到一个新变种**:兜底路径**不管有没有真的放锁都记一笔遥测**,于是正常收尾的 `done` 被 16s 后迟到的兜底覆盖成「兜底放锁」——读数看起来像**每次都走了兜底**。放锁函数改为返回「这一次是否真的执行」,只有真放了才记。**探针撒谎比没有探针更坏**(详见 §4.14)。

---

**子模式 B · 依赖了跨生命周期稳定的对象,清理后无人重排(刀 4 的守护测试发现)**

> **调度链不能挂在「会被别人清理、而自己又不会因此重跑」的定时器上。**

刀 3 的电台与远光把调度链挂在 `runtime.setTimeout` 上,effect 只依赖 `[runtime]`。而 `useSkinRuntime(skinKey, turn)` 在**换回合**时会 `teardown()` 清掉全部受管定时器 —— 偏偏 `runtime` 的**对象身份跨 turn 稳定**,所以那个 effect **不会重跑**。结果:链条被清空后再没有人重新排期,**电台与远光从第二回合起永久静默**。

探针实测(刀 4 勘察时用最小复现钉住):换 turn 前触发 3 次,换 turn 后再等 10s 触发 **0** 次。

三条推论:

- **清理与重排必须成对**。`teardown()` 清掉的东西,要么由同一个 effect 的依赖变化重新建立,要么根本不该交给它清理;
- **自持的链条走 `window.setTimeout` + 本 effect 自己的 cleanup**;一次事件**内部**的定时器仍走 `runtime`(那些**应当**被换回合打断);
- 依赖里**不要为了修这个而塞 `turn`**:那会让每次玩家做选择都把倒计时清零重来,玩家出手比间隔快时效果**永远等不到**——把「静默」换成了「饥饿」,同样是坏的。

**修复**:刀 4 一并修好刀 3 的两处(`useRadio` / `WasteAmbient`),并补 `wasteLifecycle.test.tsx` 守住;**已做变异验证**(改回原写法,三条跨回合用例立刻变红)。

**4.12 搬元素要连关系一起搬(刀 3 教训,与 F-019 / 修仙视觉复盘同族)**

刀 3 把末日表盘从样板间搬进生产时,`WASTE.ease` 与 `XIAN.ease` 在 `motion.ts` 里**恰好都是 `power2.out`** —— 直接复用会让末日与修仙的数值滚动**是同一条曲线**,四世界少一条时间感,而**代码上完全看不出问题**(两个世界各自都「用了自己的常量」)。

真正的差异在样板间不在那个常量里:末日的迟滞感靠的是**两段补间 + 启动 lag**(`delay: lag()` → `easeStart` 走前 62% → `ease` 收尾),而通用层的数值滚动刻意只吃**一个** ease(同步逻辑单点,§4.2.1)。**元素(常量)搬过来了,关系(两段编排)丢在了样板间。**

这与 [F-019](../../bakeoff/FINDINGS.md)(承载面:效果在孤立环境里成立、在真实页面里被遮掉)、§6 挂账的「修仙屏整体视觉复盘」(搬了元素没搬骨架)是**同一族**问题:**样板间成果搬进生产时,元素易搬、关系易丢**。

操作口径:移植任一效果时,先问**「它在样板间是靠什么达成的」**——若答案里含「两段」「先后」「叠加」「相对某物」,那部分关系必须显式重建或显式记为近似。刀 3 的处理是给 `WASTE` 增 `easeRoll` 单 ease 近似,并用**「三世界 ease 互不相同」的断言测试**钉住,免得下次又悄悄撞回去。

**4.13 关键守护测试必须做变异验证(刀 4 教训,通用纪律)**

> **凡「为防止某个具体失效而写」的守护测试,必须附一次变异验证记录:故意把代码改坏,确认它真的会红。**

刀 4 写「换回合后调度链仍然活着」的守护时,宿主组件每次渲染都新建一个 `rootRef` 字面量 —— 于是 `setVar → fireSpore → fireText` 逐层失稳,调度 effect 每次渲染都重跑。**结果是:把依赖里的 `turn` 删掉,用例照样通过。** 一条绿的测试,守住的却是自己造出来的假象。

**根因是一类普遍现象**:守护测试的价值全在「它会不会红」,而这件事**默认不会被验证** —— 我们只看见它绿。绿有两种解释(代码是对的 / 测试没在测),而测试套件本身**不区分这两者**。

三条操作口径:

- 写完守护测试,**立刻把它要防的那个 bug 手工植回去**,确认变红,再改回来;
- 变异验证的结论**写进测试文件的注释或 commit message**(它是证据链的一环,不是一次性动作);
- 守护测试必须复现**真实接线**(真的 hook、真的生命周期、真的 StrictMode),手动 new 一个替身往往复现不出目标失效 —— 这与 §4.9 是同一条。
- **变异验证的复原必须让编译器真的重编**(ADR-020 刀 5 教训,2026-08-10):
  `mv` / `cp -p` 一类**保留 mtime** 的手法会让增量编译跳过,**跑的是带变异的陈旧产物**。
  复原后 `touch` 相关源文件,或直接 clean。
  实例:刀 5 三条变异逐条验红后用 `mv .bak` 复原,全量一度 3 红而源码完全正确。
  **记明理由:假红比假绿容易发现,但同样会把人引向错误的修法** —— 若未查清,
  下一步很可能是去改那三个「失败」的测试。

  这一条补的是本节前三条的**盲区**:那三条管「测试有没有在测」,这一条管
  「**你以为在跑的代码,是不是真的在跑**」——与 §4.14(观测工具本身需要被验证)同族。
- **变异验证的复原不得用 `git checkout --`,除非当前工作已提交**(ADR-020 刀 7 教训,2026-08-10):
  未提交的工作区**不是备份** —— `git checkout --` 会把它退回 HEAD,
  而变异脚本通常同时删掉 `.bak`。**备份放工作区之外,复原用 `cp` + `touch`。**
  与上一条的关系:**上一条管「复原后跑的是不是新代码」,这一条管「复原本身会不会把没提交的工作删掉」。**
- **脚本化文本替换(缩进 / 空白敏感)可能静默失败,而随后的全绿是「未改动代码」跑出来的**
  (F-023 修法教训,2026-08-10):实例 —— 用脚本替换 `behaviorHint`,
  模板里的缩进比源文件多一个 tab,替换未命中;紧接着跑出来的 **354 绿是原封不动的代码**。
  **改完必须先确认替换真的发生(`git diff` 或 `grep` 新措辞),再看测试结果。**
  > **绿有多种解释:改对了、没改坏、以及根本没改。**

  **上面三条(增量编译跑陈旧产物 / 复原删掉未提交的工作 / 替换静默失败)是同一族**:
  **你以为你在验的东西,不是你实际在验的东西。** 三条的共同解法也一样 ——
  **在读测试结果之前,先证明被测对象确实是你以为的那个。**

  **第四个实例(ADR-021 刀 1,2026-08-15):对拍用的 dump 工具本身撒谎。**
  刀 1 首轮报 6/14 DIFF,而两个真因**全在工具里**:① harness 用 `Map.of` 装数值轴,
  而 **`Map.of` 的迭代顺序每个 JVM 实例都不同** → `attributes` 的 key 序在两次 dump 间随机变化;
  ② world-gen prompt 尾部**按设计随机挑场景种子**(F-005 多样性),两次必然不同。
  **四次形状完全一样**,故本条自此按「一族」读:增量编译跑陈旧产物 / 复原删掉未提交的工作 /
  替换静默失败 / **观测工具本身撒谎** —— 前三条坏在**被测对象**不是你以为的那个,
  第四条坏在**观测手段**不是你以为的那个,而读数上**四者完全一样**。
- **变异验证的复原不得用 `git checkout --`,除非当前工作已提交**(ADR-020 刀 7 教训,2026-08-10):
  **未提交的工作区不是备份** —— `git checkout --` 会把它退回 HEAD,
  而变异脚本通常同时删掉 `.bak`。**备份放工作区之外,复原用 `cp` + `touch`。**
  实例:刀 7 的变异复原写成 `rm -f $P.bak; git checkout -- $P`,
  而该刀尚未 commit → `EventLoopService` 的全部改动被删除并重做了一遍。

  **与上一条的关系**:上一条管「**复原后跑的是不是新代码**」,
  这一条管「**复原本身会不会把没提交的工作删掉**」——
  前者让你读到假红,后者让你直接失去工作;两条都出在**复原**这一步,故并列在此。

- **渲染级守护验的是结果,源码级守护验的是结构 —— 改结构的刀次,只有渲染级守护等于没守**
  (ADR-021 刀 1 立字,2026-08-15,**通用于所有重构类刀次,不限视觉**)。
  刀 1 把三条族级原则的词提到族层、世界层改为引用,守护第一版只查
  「**词在不在渲染结果里**」——于是把世界层模板的引用**退回硬编码原文**时,**测试照样是绿的**:
  词确实还在,只是又变回了一份拷贝,**而那正是那一刀要治的病**。
  补一条**源码级断言**(族级片段的词不得出现在世界层源文件里)后才变红。
  > **判据**:先问「这一刀改的是**结果**还是**结构**」。改结果(数值、文案、时序)→ 渲染级守护够;
  > **改结构(谁持有它、它从哪来、由谁引用)→ 必须有一条断言直接看结构本身**,
  > 因为结构变了而结果不变,**正是重构类刀次的成功定义** —— 渲染级守护在这种刀次里
  > **天然测不出任何东西**。
  与上面几条同族:绿有两种解释,而这一次「绿」是**测试问错了问题**,不是测试失稳。

- **凡是遍历清单的守护,清单本身必须另有一条守护**(ADR-021 刀 2 立字,2026-08-15,**通用**)。
  刀 2 把时钟契约从族级片段清单里删掉时,**全部 lockstep 照样是绿的** ——
  因为它们**都遍历那份清单**,清单短了就不再检查那一条。
  > **守护没坏,是它的检查范围被悄悄缩小了。**
  这与「守护测试假绿」同族但**更隐蔽**:假绿是断言写坏了、还看得出可疑;
  这一种**每条断言都完好、每条都在认真执行**,只是**要验的东西少了一件**,
  而读数(全绿)与「全都验过了」**完全一样**。
  解法:按**身份**逐条钉死清单(不是按数量 —— 数量对了也可能换了内容)。
  同族的还有:遍历「全部已激活 archetype」「全部注册主题」「全部族成员」的守护,
  一律要问一句「**这份清单本身谁在看**」。

- **机制话术不得复用世界层的词**(ADR-021 刀 2 立字,2026-08-15)。
  刀 2 的禁词守护(机制文件里不得出现人类年龄段与阶段名)**首跑就响**,
  抓到的是 `LifeStageTable` 的一句**异常文案**里用了「末段」——
  那里的「末段」指「阶段列表的最后一段」,与《寻常》那个叫「末段」的人生阶段**毫无关系**。
  **改文案、不改守护**(异常文案改说「最后一个阶段」)。
  立字理由:**机制层的话术与世界层的词共用同一个字面量,会让禁词类守护无法区分「泄漏」与「巧合」** ——
  而一个分不清这两者的守护,迟早会被人调松,然后就再也抓不到真泄漏了。
  与下一条(误报同样危险)同源:**守护要能被信任,前提是它不喊狼来了。**

- **守护弱化的第四形态:探针只对人眼可见,没有断言在看**(ADR-021 刀 3 立字,2026-08-15,**通用**)。
  前三种形态里,<b>至少还有一条断言在测错东西</b>(测试写坏 / 检查范围被缩小 / 指标不匹配);
  这一种<b>根本没有断言</b> —— 「探针」只活在**人的检查步骤**里(冒烟清单的一行、brief 的一句 ⚠️),
  而<b>人会忘、会换人、会赶时间</b>。
  实例:刀 3 的探针是「prompt 里出现动物处在『31–55 岁』= 参数化没生效」。
  变异验证把 `animal_life` 映射到《寻常》那张表时,**登记面对拍照样通过**(键还在)、
  **全部 371 个测试照样绿** —— 那句探针一次都没被执行,因为**没有任何东西在执行它**。
  > **判据:凡是写进冒烟清单或 brief 的「探针」,必须问一句「谁在自动看它」。**
  > **没有答案的探针不是守护,是备忘录。**
  补的两条里,**「加载期 key 必须等于表自称的 archetype」是更根本的那条** ——
  它在**数据层**否掉错配,不依赖 prompt 是否被渲染、也不依赖有没有人去读那段 prompt;
  prompt 级那条只是第二道(因为「挂错表」不止「键写错」一种走法:照抄一张表的内容时 key 是对的)。

- **取证手法本身会破坏被取证的对象**(ADR-021 刀 3 扩,**同族不同机制,故必须两条都记**)。
  §4.13 已记过一次:刀 7 的变异复原用 `git checkout --`,**把未提交的工作删掉并重做了一遍**
  (机制:**命令语义** —— `checkout --` 就是「丢弃工作区改动」)。
  刀 3 又中一次,**机制不同**:为取 BASE dump 把两个**已 tracked** 的文件 `mv` 到别处再 `git stash`,
  `stash pop` 时把**刚写好的动物时钟表整个删掉**(机制:**stash 对 tracked / untracked 的差异处理** ——
  文件在 stash 时缺失,于是「删除」被一并存进 stash 并在 pop 时还原)。
  > **两次同族、机制不同,所以「下次小心」拦不住第三次。**
  **正解不是更小心,是把那个步骤取消掉**:刀 3 改用「**harness 跳过 registry 不认识的世界**」——
  同一份 harness 能直接跑两个构建,**「动文件树」这个步骤本身不再存在**。
  > **消除步骤优于小心执行步骤。**
  同族可套用处:任何需要「临时把文件挪开 / 临时改一个值 / 临时插哨兵」的取证,
  先问一句「**能不能让工具自己适应两个构建,而不是让工作区在两个构建之间来回搬**」。

本 ADR 范围内已按此纪律留下记录的:§4.9(入场守卫记「已开演」)、§4.11 子模式 B(调度链跨回合)、§4.2「认标不认 key」(刀 2.5 把分派临时改成读 key,两条用例当场变红)。

**4.14 观测工具本身需要被验证(刀 4 教训)**

> **探针上线前必须自验一次:正常路径与异常路径的读数确实不同。**

本项目的方法论高度依赖时序探针 —— §5 Q7 立的字是「**先接探针再调体感**」,刀 1 靠它把「灯闪到底有没有发生」从凭感觉猜变成读数二分。**正因为如此,探针撒谎的代价比没有探针更大**:没有探针时人会保持怀疑,有一个说谎的探针时人会相信它。

刀 4 的实例:兜底放锁路径**无条件**记一笔遥测,于是正常收尾写下的 `completed … state done`,在 16s 后被迟到的兜底覆盖成 `state 兜底放锁`。读数上看,**每一次事件都像是走了兜底** —— 而实际一次都没有。若不是恰好在同一次冒烟里观察到完整时序,这个假象会一路带进真机冒烟,并让人去「修」一个根本不存在的问题。

操作口径:

- 探针记录点若挂在**多条可能路径**上(正常收尾 / 兜底 / 被打断),每条路径必须能在读数上**被区分**;
- 幂等收尾函数应返回「**这一次是否真的执行了**」,由调用方据此决定记不记 —— 而不是「反正调了就记」;
- 冒烟时**至少完整观察一次正常路径的全时序**(scheduled → fired → completed),确认它不被后续事件覆盖。

**4.15 结构线跟随全局色温,物件表面可有自己的材质温度(修仙屏视觉收敛批立字,Felix 2026-07-31)**

> **边框、分隔线、描边这类**结构线**必须跟随全局色温;卡片 / 签面 / 纸面这类**物件表面**可以保留自己的材质温度,不算色温断裂。**

收敛批把整屏移到雾青之后,玉简签上出现两处暖色残留,而它们的性质**不同**:

- **边框**(`rgba(120,105,60,.26)`)—— 全屏唯一还偏暖的**结构线**,它是刀 2 暖调色板的残留,与「卡片奶白→雾青」是同一件事 → **改**(已改为 `rgba(58,88,92,.26)`,与 `--line` 同色相);
- **签面底**(合成后约 `rgb(243,246,246)` → `rgb(233,236,232)`,B 比 G 仅低 4、肉眼近中性)—— 玉简是**薄玉 / 宣纸的物件感**,纸面本就该比环境略暖一点点 → **不动**,那是**材质**,不是断裂。

立这条是为了防**反向过度**:收敛轮很容易滑成「见暖就清」,把材质感一并洗掉,最后四个世界的物件都变成同一种无质感的灰片。判据是问**「这个暖色在承担什么」**——描边界、分区块的,归色温统一管;表达材质、表达物件是什么做的,归世界视觉语言管(ADR-017 §6 每世界视觉语言表)。

**4.16 对比度要算文字**实际叠在什么上面**,不是算平均底色(修仙屏视觉收敛批教训)**

> **底色是渐变 / 多层叠加时,取**该文字所在位置的最悲观那一层**反推颜色,不能拿平均底色或顶层底色代算。**

收敛批实例:境界印的印面是渐变,且印面之上还压着一层**印泥**(`.sealFill`,金,高度 = 当前值)。按印面平均底算,`#4e5654` 得 5.6:1 —— 「看着够了」;但**数字恰好落在印的下部,压在金色印泥那一端**,该处实测只有 **4.29:1**,不达标。改取「印泥渐变两端都叠上」的最悲观底反推,降到 `#474f4d` 才两处都过(印面 6.26 / 印泥处 4.79)。

这与 [runbook §3.1.5/§3.1.6](../phase3-fly-deploy-runbook.md)「**先证明环境是你以为的那个,再验功能**」**同族**:两者都是**先把被测对象的真实环境搞清楚,再下判断** —— 那边是「你以为线上跑的是新镜像/真 key」,这边是「你以为文字底下是那块平均色」。操作口径:

- 半透明卡片时代的对比度**必须逐层合成实测**(读 `getComputedStyle` 的每层背景按 alpha 叠),不能拿设计稿上的色号算;
- 底色有渐变 / 有随数值变化的覆盖层时,取**最坏位置**;
- 报数时写清**测的是哪一处底**(本批两个数都报了:印面 / 印泥处)。

**4.17 差异只在样式 → 加 class 令牌;差异在 DOM 结构 → 才开组件槽(线 C 立字,Felix 2026-08-01)**

> **判据只有一条:四个世界的 DOM 需不需要长得不一样。**
> 需要 → 开**可选组件槽**;不需要(差异 100% 在 CSS)→ 加一个 **class 令牌**,通用组件照旧只有一个。

立这条是因为刀 3 与刀 4 各开了一个可选槽(`Interlude` / `Prose`),**两次都对**,但它们很容易被当成
「主题层要什么就开个槽」的先例 —— 那会一路滑到「每个控件一个槽」,而槽越多,通用层能保证的东西越少。

- **刀 3 `Interlude` 开槽是对的**:电台是**正文与决策圈之间的一个独立区块**,那个位置此前根本不存在;
- **刀 4 `Prose` 开槽是对的**:文字异常必须作用在**分片 span** 上,正文 DOM 结构本身必须不同;
- **线 C 返回键不开槽是对的**:四种形态(方角等宽 / 切角玉牌 / 铆钉铁皮 / 微倾纸条)**全部是 CSS**,
  DOM 都是同一个 `<button onClick={reset}>`。开槽 = 四套皮肤各抄一遍同一个按钮,
  **是抽象腐坏的反方向** —— 通用层从此不再能保证「每个世界都有出口」,而那恰恰是这个控件唯一要保证的事。

**行为差异怎么办**(线 C 的真实边角):克苏鲁要求返回键**按压时长每次不同**(「节奏不可信」),CSS 做不到。
解法**不是**为它开槽、也**不是**加一个 `isCthulhu` 式的开关,而是照 `ValueRoll.durationMs` 的既有形状加一个
**时间感参数** `backPressDurMs?: number | (() => number)`:**皮肤给值、通用层施加**,任何世界都能给个常数,
参数名里不出现世界。判据推论 —— **参数化的是「多久」,不是「谁」**;一旦你想写的字段名里出现世界名,就说明选错了形状。

**4.18 观测指标要与被测对象匹配 —— 问对问题,而不只是量对数(线 C 教训)**

> **先说清「我到底要保证什么」,再挑指标。指标与目标错位时,读数会把**形态**报成**缺陷**。**

线 C 实例:验返回键热区,第一版测**外接矩形的四角**是否可点 —— 结果规则怪谈过,修仙 / 末日 / 克苏鲁**全失败**。
但那三个世界恰恰是用 `clip-path`(切角)与 `transform: rotate`(微倾)做形态的,**外接矩形的角本来就不属于按钮** ——
形态是对的,指标问错了。我们要保证的是「**手指能不能点到**」,不是「**外接矩形完不完整**」。
改测「以按钮中心取一个 44×44 正方形,9×9 网格逐点 `elementFromPoint`」后,四世界 **81/81** 全过。
(顺带:最后一排恰在 `bottom` 边界上会落空,是半开区间的取样假象,内缩 0.6px 即消失 —— 这也属同一类「指标细节」。)

与 **§4.14(观测工具本身需要被验证)同族,但不是同一条**:§4.14 管的是**工具会撒谎**(探针记了假数据、
`innerWidth` 读到 0);本条管的是**工具没撒谎、指标问错了** —— 读数完全真实,却在回答另一个问题。
操作口径:**红了先问「这个红对应哪一条我真正要保证的性质」**,答不上来就是指标选错,而不是产品有缺陷。

**4.19 通用 token 不等于安全 —— 跨世界复用必须逐世界实测对比度(线 C 教训)**

> **同一个通用变量,在四个世界各自的合成底色上表现可以完全不同。复用 token 只是省了取色,不免除逐世界实测。**

线 C 实例:返回键最初直接用 `var(--muted)`(四个世界都有,看起来天经地义)。实测:
规则怪谈 **3.51**(`--muted: #5f6d78` 压在按钮自身暗底上,**连 WCAG AA 的 4.5 都不到**)、末日 5.43、修仙 5.82 ——
三个世界低于本项目 §4.6 的 ≥6.3 口径,而且**这是导航控件,不是氛围性装饰文字**:玩家找不到出口,
比看不清一条规则严重。改用各世界**已经为次级文字校准过**的 `--rule-idle`(修仙玉牌更亮,再单独压一档),
四世界 6.67 / 6.68 / 6.79 / 6.77 全部达标。

根因:`--muted` 在各世界的语义是「**氛围性次级文字**」,它的校准底是**卡片**;返回键的底是**它自己的背景**
(叠在氛围图与渐变之上),两者不是同一块底。与 **§4.16(对比度要算文字实际叠在什么上面)同族** ——
§4.16 说的是「同一个世界内别算错底」,本条说的是「**换了世界,底也换了,token 的达标结论不跟着走**」。
操作口径:**任何 token 被一个新控件复用时,四个世界各测一遍**;达不到就在该控件上单点覆盖,
**不要去改共享 token**(那会把一个控件的问题扩散成全屏的问题)。

**4.20 移动端手势三条(线 B1 原型教训,B2 会直接复用)**

> **在纵向可滚动的列表里做拖拽,难的从来不是「拖」,是「不抢玩家的默认手势」。**

本条不是视觉移植的产物,而是[线 B1 融合入口拖拽手势原型](../proto-b1-fusion-drag-smoke.md)验出来的
**移动端通用知识**;放在这里是因为 §4 已经是本项目前端实现教训的单一落点(§4.11 定时器 / §4.13 变异验证 /
§4.14 观测工具 / §4.18 指标 / §4.19 token 复用同理)。三条都在 `web/src/proto/FusionDragProto.tsx` 文件头有对应注释。

**(a) `touch-action: pan-y` 保住原生惯性滚动 —— 写 `none` 等于没收玩家的默认手势。**
纵向滚动交回浏览器(带惯性、走合成器、不过主线程),只把**横向**留给自己判定。
图省事写 `touch-action: none` 能让拖拽实现变简单,代价是这个列表从此不会惯性滚动了 ——
而「上下滑」正是玩家在世界列表上的**默认动作**,拖拽只是叠加语义。**默认手势优先级高于新手势。**

**(b) `touch-action` 在触摸序列开始时就定死,中途改无效 —— 抓起之后要挡滚动,只能靠非 passive 的
`touchmove` + `preventDefault`。**
这是最容易踩空的一条:很多实现会在进入拖拽态时动态改 `touch-action`,看代码非常合理,**运行时毫无作用**
(浏览器在 hit test 那一刻就读完了)。可行的只有 preventDefault,而它要求监听器 `{ passive: false }`。
配套纪律:**监听器在 `pointerdown` 挂上、手势结束(up/cancel)即摘,不常驻** ——
常驻的非 passive `touchmove` 会让**每一次普通滚动**都先过一遍主线程,
等于为了拖拽把滚动手感整体拖慢一档(而滚动手感恰恰是这一刀要测的东西)。

**(c) 逐帧数据直接写 DOM,不走 setState —— 观测工具不该扰动被观测对象(§4.14 同族)。**
拖拽的 transform 与屏上读数都是每帧变的;若走 state,一次拖拽就是几百次整页重渲染,
**测出来的卡顿分不清是拖拽实现的问题还是观测方式的问题**。做法:逐帧量(transform、HUD 文本)
直接写 DOM 节点,**只有离散变化**(抓起了谁 / 命中了谁 / 是否可提交)才 setState。
与 §4.14 的关系:那条说**探针会撒谎**,这条说**探针会改变现场**——两种失效都会让读数不可信。

### 5. 其余七问裁定(入档)

**Q2 · 融合局的游戏内视觉**
已定调:入口互噬 / 局内 host 打底 / foreign 走安全渗漏签名 / 共享低频槽位 / 不挂业务轴 / per-combo 只碰文案封面与静态标记。
**但签名未实现前,融合局纯 host 呈现**(同 `scene.ts` 未配图即降级的先例),**不阻塞基础移植**。详细方案挂 **ADR-019**(尚未开写)。

**Q3 · 形近字表**
**100–200 对人工允许表**,入选标准:常用字 / 该字体下肉眼近似 / 替换后不荒诞 / 无罕见异体字 / 不依赖特定字体。
**不用 Unicode 相似度运行时推断**(推断出的「近似」在实际字体下经常不近似,且会撞出荒诞语义)。
**找不到候选即切换其余五型异常,不强行降质**。
AI 标注异常字方案挂 [future-experience-backlog](../future-experience-backlog.md)(依赖 structured narrative schema)。

**Q4 · 克苏鲁文字异常的启动条件(回改 ADR-017 §6.3)**
以样板间实现为准:**全程极低频 + san 调频率**,而非「san<20 才启动」。
**理由**:异常只在低位启动,会使「异常出现」本身成为**状态播报**——玩家看到一次扭曲就知道自己进了危险区,记忆点退化为状态指示器。
补上下界立字:

- 高 san:极低频,但**非绝对零**;
- 低 san:仍保持**长沉默**与**不可预测**;
- **任何状态都不得形成周期**(防止玩家用频率反推状态)。

**Q5 · 修仙钟鸣的触发条件**
挂 `realm` **向上**跨 band(`newBandIndex > oldBandIndex`;**下跌不鸣**)。

- init/resume **首次装载不触发**(须已有前值 → 新 turn 值 → 向上跨档);
- 一次跨多档**只鸣一次**;
- **钟鸣期间新 turn 到达**:数值按真实 turn 更新,当前 timeline 安全收尾或快速归位,**不排队补播**——**仪式感不以状态滞后为代价**;
- `bands` 缺省则不触发(静默降级)。
- 「盯 `realm`」属**主题注册表的按 key 配置**,**锁在注册表内,不得渗进通用数值组件**。

**Q7 · debug 入口**
仅 `?debug=1`。**长按标题不进生产**(该手势已被选择屏的融合渗漏占用)。
`debug` 参数**不写入持久状态**;debug 控件**不得改变生产数据**,只允许触发前端展示与查看调度状态。

**效果时序遥测(刀 1 落地,范式保留供刀 2/4 复用)**:`theme/telemetry.ts` 记 `scheduledAt / firedAt / completedAt / suppressedReason / state / activeClass`,`?debug=1` 面板逐行读。这条探针在刀 1 当场把「灯闪到底有没有发生」从**凭感觉猜**变成**读数二分**(直接坐实序列在 StrictMode 下根本没触发,见 §4.9 与 [F-019](../../bakeoff/FINDINGS.md))。**刀 2 钟鸣、刀 4 异常调度这类「有没有发生、被谁抑制」难以肉眼判定的一次性/低频效果,一律先接这条探针再调体感** —— 不接探针就调强度是刀 1 已证明的弯路。纪律:只记时间戳与原因,不参与生产逻辑、不写持久状态。

**Q8 · 测试双层**

- **共享语义断言**:value / displayName / 当前 band label 可读、severity 正确映射、`bands` 缺省不崩、未知 severity 安全降级;
- **每形态一条特征元素存在性冒烟**。

**不断言 DOM 层数 / 像素 / 分段数量 / class 排列**——同 golden 哲学:**护城河守行为,不守像素**。

## 关键理由

1. **语义产出方原则第三次实例化,形状与前两次完全一致**。ADR-010 让 AI 标 `outcome`、引擎只读;ADR-011 让 AI 写 `hint`、引擎不裁决;本次让服务端派生 `severity`、前端只渲染。三次都是同一个判断:**让消费方去猜生产方才知道的事,是可预见的错误来源**——而且错法都一样(消费方会发明一套启发式,启发式在新世界/新组合上失效)。
2. **`perilAtHigh` 换来的是融合世界的零登记**。它不只是让禁忌知识出 danger:因为 `AxisSkin` 不换该标,两个融合组合的道心与补给自动继承 host 侧派生结果,per-combo 对 severity 一行不写。这与 F-016 的复用成本模型对齐——视觉层不给「加一对组合」的代价再加一项。
3. **严守引擎无知**。`lethal` 是引擎会读的字段,为了染色去改它会静默改变触底与结局 gate 行为;新加一个引擎不读的展示位,是唯一不污染内核的做法。
4. **降级方向恒为「安静」**。四种缺省情形一律不进危险态。视觉宪法第一条(内容永远第一,唯一一票否决项)在这里的具体形态:**不确定时,不吓玩家**。
5. **试验田 + feature gate 让刀 1 可回退**。只有规则怪谈登记新主题,出问题删一条注册即回退——不必在四个世界都上线之后才发现基建有结构问题。

## 已知代价

1. **元数据面继续变厚**:`AttributeAxis` 现有 8 个字段,再加 `perilAtHigh` = 9。缓解:它是引擎不读的展示位,新加世界不配即默认 `false`(安全方向)。
2. **`perilAtHigh` 是人工判断,可能配错**:没有机制能验证「这根轴高位到底危不危险」。缓解:它只影响染色、不影响任何判定;配错的后果是一根轴少染或多染一档色,不影响游戏逻辑。
3. **severity 是三档粗粒度**:样板间某些世界的危险表现是连续的(渐变而非跳档)。本批不做连续映射——三档对齐已有的三 band 结构,连续映射需要前端拿到更多语义(违本 ADR 的原则)。若后续确有需要,应扩 severity 取值而非让前端插值。
4. **刀 1 后的一段时间里,四世界视觉不一致**(规则怪谈新、其余三个旧)。这是 feature gate 的代价,也是它的目的;若中途暂停,不一致状态会停留更久。
5. **`?debug=1` 是生产可达的入口**:任何人拼 URL 即可打开。缓解:debug 控件不得改变生产数据、不写持久状态,最坏情况是玩家看到一些调度信息。

## 重新审视的触发条件

- **前端出现「想按 key/label 判断点什么」的第二次冲动**——说明 severity 三档不够用,回窗口讨论扩取值,**不得就地发明启发式**;
- **某个融合组合的 severity 需要 per-combo 覆盖**——说明「换皮不换 `perilAtHigh`」的假设破了,须回 ADR-012/014 的换皮清单重新对齐;
- **刀 1 的主题注册表被要求承担轴语义**(如「这个主题下 hp 要特别处理」)——说明通用层/主题层的切分位置错了,回头改切分,不在主题层堆特例;
- **记忆点数量超过一级表**(AGENTS.md Motion Constraints §2 的唯一表)——按 ADR-017 §9「新增须替代或降级」处理,不得只做加法。

## 实施步骤

1. **刀 0 · 后端**:`AttributeAxis` 增 `perilAtHigh` + severity 派生(挂已排序的 `bandRanges()`),`GameInitService.attributeMeta` 下发;init/resume 同一路径。
2. **刀 0 · 前端**:更新 TS 类型与兼容解析(`severity` 可选字段,四种缺省安全降级);**不上皮肤、不改渲染**。
3. **刀 0 · 测试**:① 境界(accumulation,`perilAtHigh=false`)高位 `neutral` ② 禁忌知识(accumulation,`perilAtHigh=true`)高位 `danger` ③ 气血(致命 depletion)低位 `danger` ④ 四种缺省情形安全降级 ⑤ init 与 resume 得到相同 severity ⑥ turn delta 只更新 value 后,前端用 init 保留的 `bands` 正确重算当前档 ⑦ 两个融合局的 severity 与各自 host 单体一致。
4. **刀 1–4**:各自独立工作单元,按 §3 范围与「不准顺手做什么」执行。
5. **ADR-019**:融合局游戏内视觉(Q2 详细方案),尚未开写。
