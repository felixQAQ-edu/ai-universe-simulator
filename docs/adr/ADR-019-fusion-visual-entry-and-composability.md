# ADR-019 · 融合视觉:入口互噬、局内单主语,与「四套材质覆盖六对组合」的可组合机制

- **日期**:2026-08-04
- **状态**:已采纳
- **决策者**:Felix

## 背景

ADR-018 四刀走完,四个基础世界(规则怪谈 / 修仙 / 末日 / 克苏鲁)全部登记了自己的皮肤;
融合世界在游戏内一直走「纯 host 呈现」的降级路径(ADR-018 §5 Q2 明确把详案挂到本 ADR)。
与此同时,融合**入口**仍是 ADR-013 决策 4 立的「误入手势 + 渗漏卡」:依次长按两张卡,
多出一张渗漏卡。线 B1(2026-08-03)验证了 Felix 提的新入口设计——
**把 A 卡拖到 B 卡上,被拖者 = foreign、承接者 = host**,真机六条全过、结论 (a) 顺手,
「拖拽范式在纵向可滚动列表里成立」这个承重假设被证实。

于是本 ADR 要一次性回答两个被 B1 结论解锁、又一直悬着的问题:

- **入口**:碎解揉合的强视觉怎么做,才不至于变成「为每一对组合画一套动画」;
- **局内**:融合局的视觉签名(ADR-018 §5 Q2 挂账)按什么约束设计,才不会在
  50+ 回合的持续阅读里撞视觉宪法第一条。

约束条件:

1. **F-016 成本模型**:加一对融合组合的代价必须保持在「后端数条纯文案 + 前端数条登记」,
   引擎/校验/骨架结构零改(ADR-014 已把这个代价结构量化过一次)。视觉不得成为新的
   per-combo 成本项。
   > ⚠️ **补充(2026-11-05,见文末「订正」§5;上句原文不动)**:视觉登记(一份标志资产,纯数据)
   > 是 per-combo 的**可选**成本项;不登记即降级为交叉淡化,加一对组合的最低成本仍是「文案 + 登记」。
2. **视觉宪法第一条(ADR-017)**:内容永远第一,是唯一的一票否决项。
3. **动效预算(AGENTS.md Motion Constraints §2)**:每屏 1 持续环境 + 1 低频偶发 + 1 用户触发。
4. **`schemaVersion` 保 "0.4"**;引擎/校验/prompt lockstep 零动。
5. 依赖白名单 = GSAP / Lenis(Motion 已于刀 4 移出,ADR-017 §3.1 修订自身)。

### 勘察发现:「接 registry」与「后端零动」互斥(本 ADR 的第一处事实订正)

B1 收口时立的挂账是「B2 必须接 registry,否则玩家会拖出一个后端 400 的组合」。
实施前勘察发现:**现有 API 完全不投影 `FUSION_COMBOS`** ——
`GET /api/archetypes` 只下发 `ArchetypeSummary{archetype,displayName,tagline,vibeTag,active}`,
而 `FUSION_COMBOS` 是 `ArchetypeRegistry` 的 private static Map,只经 `isFusionSupported` /
`fusedAxes` 在 init 路径内部消费。前端今天的合法组合来自 `fusion.ts` 的 `FUSION_GESTURES`
硬编码两对——也就是说**双真相源今天就已经存在**,B1 只是没有让它变得更糟。

Felix 裁定(2026-08-04):brief 里的「后端零动」是错误前提,以勘察事实为准;
维持双真相源是本项目一路在防的东西(ADR-002 口径散落三处、AGENTS/CLAUDE 双份全文漂移、
ADR-018 §4.1「判定只发生一次」),且后果具体——玩家能拖出一个后端 400 的组合。

## 候选方案

### 入口视觉 · 方案 A:per-combo 特供揉合动画

**优点**:
- 每一对组合都能做到叙事上最贴切(识海遗蜕的金光撞冷蓝、人防工程的锈土压守则)。

**缺点**:
- **直接违反 F-016 成本模型**:六对组合 = 六套动画,世界库 backlog 规划到 14 个世界时
  组合数是 O(N²),而资产是手工的。
- 与 ADR-014 刚刚花一整刀把 round-1 硬编码文案收回槽位的方向相反。

> ⚠️ **订正(2026-11-05)**:方案 A 的否决理由**不变**。2026-11-05 的订正让每对组合的「标志」各不相同,
> 但**没有违反它** —— 理由见文末「订正」§5。

### 入口视觉 · 方案 B:统一一套通用碎裂动画

**优点**:
- 成本最低,加世界零成本。

**缺点**:
- **入口那一秒的全部价值就是「两个世界撞在一起」**,而通用碎裂让四个世界碎得一模一样,
  等于把这一秒降级成一个转场特效;玩家分辨不出撞进去的是哪两个世界。

### 入口视觉 · 方案 C:四套 per-world 碎解材质 + 四套独立物理(本 ADR 采纳)

> ⚠️ **已作废(2026-11-05)**:四套材质与四套物理整体退役,由「共用骨架 + 可选登记标志」取代,见文末「订正」。
> 下文原样保留,作为当时的决策记录。

每个基础世界维护**一套自己的碎解材质与碎解物理**,组合动画 = 左右两侧各放各的材质、
各走各的物理,中段揉合与展开共用同一条五拍骨架。

**优点**:
- **资产随世界数线性增长(N),覆盖组合数 O(N²)** —— 这正是 F-016 成本模型要的形状。
- 一眼可分辨:四套在轮廓 / 边缘 / 尺寸分布 / 运动倾向四个维度上刻意拉开,不是换个颜色。
- 加一个新世界 = 加一套材质 + 一套物理,自动获得与所有既有世界的组合表现。

**缺点**:
- 四套物理不共用曲线,代码量比方案 B 大;每套物理要单独调。这一条是**刻意付的钱**:
  动画里玩家看到的主要是**过程**,形态只是结果——共用曲线等于四个世界只是碎片长得不同,
  碎法一样(与 ADR-018 §4.12「搬元素要连关系一起搬」是同一条教训的正面应用)。

### 合法组合真相源 · 方案 1:扩 `GET /api/archetypes` 加 `fusions`(本 ADR 采纳)

**优点**:
- 一次请求拿到世界表与组合表,**天然同源**、不可能出现两个响应不同步。
- 加一个 key 比加一个端点面轻;`ArchetypeController` 仍是薄适配、只读 registry。

**缺点**:
- 破了本轮 brief 的「后端零动」——但那个前提本身与「接 registry」互斥(见背景)。

### 合法组合真相源 · 方案 2:新开 `GET /api/fusions`

**缺点**:多一个端点面、两次往返、两个可能不同步的响应。排除。

### 合法组合真相源 · 方案 3:继续前端登记,接 registry 再挂一轮

**缺点**:维持一个**已知会漂移的双真相源**,且后果具体(玩家拖出后端 400 的组合)。
再延一轮只是债多滚一轮。排除。

## 最终决策

### 1. 核心原则:入口互噬,局内单主语

两个场景的正确解**不同**,这是本 ADR 最要紧的一句:

| | 入口(选择屏) | 局内(游戏屏) |
|---|---|---|
| 玩家停留 | 约 1 秒 | 50+ 回合的持续阅读 |
| 任务 | 宣告「两个世界撞在一起」 | 能读下去,同时还有世界感 |
| 结论 | **允许强视觉**(碎解、互噬、揉合) | **host 打底,foreign 只低频渗漏** |

**入口的强视觉不得带进游戏内。** 这不是保守,是两个场景的任务不同:
入口的强度服务于一次性的宣告,局内的克制服务于可持续的阅读。

> ⚠️ **订正(2026-11-09;上文原文不动)**:入口不再演任何揉合动作,表中「允许强视觉」一格作废;「入口的强视觉不得带进游戏内」照旧成立(入口现在没有强视觉可带)。见文末「订正(2026-11-09):入口去动画」。

### 2. 可组合机制,否决 per-combo 特供 UI

四个基础世界各维护一套**可复用资产**,六对组合自动覆盖:

- **入口侧 = 碎解材质 + 碎解物理**(本轮实现);
- **局内侧 = 安全渗漏签名**(B2-局内实现,本轮只立字)。

**不为任何一对组合编写专属流程。** 组合表只决定「哪两套资产同台」,不决定「怎么演」。

> ⚠️ **修订(2026-11-05;上文原文不动)**:「不为任何一对组合编写专属流程」**保留**。补一句:
> **每对组合可选登记一份标志资产(纯数据)**,即 SVG 轮廓、配色和揭晓边界方向。所有组合共用同一套时间线
> (交接 → 停顿 → 标志 → 揭晓),标志统一以「沿路径烧出来 / 显出来」的方式出现;没有登记的组合自动降级为交叉淡化。
> 「入口侧 = 碎解材质 + 碎解物理」一条已作废。详见文末「订正」。
>
> ⚠️ **作废(2026-11-09;上文原文不动)**:上面这段「可选登记一份标志资产 + 共用时间线 + 降级为交叉淡化」整体作废。「不为任何一对组合编写专属流程」照旧成立,且入口不再需要任何 per-combo 视觉资产。见文末「订正(2026-11-09):入口去动画」。

### 3. 五拍结构与四套物理(入口侧,本轮实现)

> ⚠️ **已作废(2026-11-05)**:五拍 1000ms、世界核、四套碎解材质与四套物理整体退役。
> 现行结构见文末「订正」§2–§3。下文原样保留。

五拍时长定案 B,合计 1000ms:

| 拍 | 时长 | 内容 |
|---|---|---|
| 挤压 squeeze | 200ms | 两张卡被拉向接触中心,压扁、略微扭曲 |
| 碎解 shatter | 180ms | 卡面让位,各自释放专属材质 |
| 揉合 knead | 260ms | 两种碎片围绕很小的中心互噬,压缩成世界核 |
| **停顿 hold** | **140ms** | **世界核停住半拍——新世界诞生前的重量,不可省** |
| 展开 unfold | 220ms | 不是爆炸,是一张被揉皱的纸重新展开 |

四套碎解材质(形态)与四套碎解物理(过程):

| 世界 | 材质 | 物理(**这条是本轮最重要的移植内容**) |
|---|---|---|
| 规则怪谈 | 硬边直角空心框 + 淡填充 + 中段切口截面 | **被裁切**:档位化位移、`steps` 阶跃、零旋转 |
| 末日生存 | 多角不规则块 + 微尘 | **崩落**:一律向下、加速下坠、大块先塌微尘后扬 |
| 克苏鲁 | 无形墨雾团为主 + 附着弯曲湿纤维 | **被拖走**:同向抽走、黏连者滞后牵动 |
| 修仙 | 浅弧实心薄玉片 + 柔性光丝 | **化散**:光丝先起托举、玉片后散、越靠近核越淡 |

**四套不共用运动曲线。** 共用曲线在代码上完全看不出问题,但玩家看到的是过程——
四个世界碎法一样,材质差异就只剩「碎片长得不同」。

### 4. 安全渗漏签名的约束(局内侧,本轮只立字、不实现)

融合局的 foreign 签名必须同时满足六条:

1. **与一级记忆点同源,但不是缩小播放**。四个记忆点性质根本不同(钟鸣是主动触发的仪式、
   灯闪是环境异常、文字异变作用于阅读内容本身、电台是整套内容系统)——机械降级会把
   最危险的那个(文字异变)渗进别人的正文,**直接撞原则 ①**。
2. **只能作用于通用表面**(氛围层 / 粒子 / 边框 / 正文区 / 色温),
   **不得要求 host 提供特定组件**。反例:克苏鲁签名不得用「刻度错位」——host 若是规则怪谈,
   那个位置只有 OSD 分段条。一旦签名依赖 host 的具体组件,N×M 适配矩阵重现,可组合模型垮掉。
3. **与 host 低频事件共享同一低频槽、代码保证互斥**(AGENTS.md §2.1 三条防滥用全部适用)。
4. **不挂业务轴、不改数值 / 选择 / 叙事结果** —— 渗漏是氛围信号,不假装成机制。
5. **默认统一渗漏权重,偏离必须记账** —— 防 per-combo 调参会话把成本模型悄悄吃回去。
6. **签名缺失时融合局纯 host 呈现,不报错不阻断**(同 `scene.ts` 未配图即降级的先例,
   也是 ADR-018 §5 Q2 现行降级路径的延续)。

### 5. host 真相源与方向语义

- **host 真相源 = `world.archetypes[0]`**,不增设冗余字段。
- 入口的方向语义 = **被拖者 foreign、承接者 host**,提交时直接生成有序双值
  `[target, dragged]` 喂 `init`(ADR-013 已立「init 收有序双值、host 在前」)——
  **动作本身表达语义,不新增字段**。

### 6. 合法组合只读投影(后端唯一改动)

`GET /api/archetypes` 响应加一个 key:

```json
{
  "archetypes": [ { "archetype": "...", "displayName": "...", "tagline": "...", "vibeTag": "...", "active": true } ],
  "fusions":    [ { "host": "cultivation", "foreign": "rules_creepy", "key": "cultivation×rules_creepy" } ]
}
```

**改动性质**:纯只读投影 —— 引擎 / 校验 / state schema / prompt lockstep 零动,
`schemaVersion` 保 "0.4"。它不是新语义,是把**已有的 registry 事实**暴露给消费方,
与 severity 契约(ADR-018:服务端派生、前端只渲染)**同族**:
**语义产出方是掌握语义的那一层,消费方无知**。前端据此判定「这两张卡能不能揉」,
per-combo 展示文案(融合卡标题 / tagline)仍留在前端——那是展示层,后端没有也不该有。

### 7. 现行长按渗漏入口退役(记明理由,免得日后被当成误删)

ADR-013 决策 4 的「误入手势」(依次长按两张卡 → 渗漏卡渗出)**本轮退役**,
`FUSION_GESTURES` 状态机与 600ms 长按一并删除。理由是技术性的,不是偏好:

- 拖拽抓起阈值 180ms(B1 真机验过的判据)**是 600ms 长按的真子集**。拖拽上线后,
  玩家每一次长按都会先在 180ms 进入拖拽态并接管指针序列 ——
  **两者并存在实现上只能靠「让长按永不触发」**,那名义上是并存、实际是
  「长按已死但代码还留着」,是最坏的形态。
- 要保住长按就得换掉拖拽的抓起方式,而那正是 B1 真机验过的判据,改了等于 B1 结论作废、要重验。
  用一轮真机验证换一个即将被取代的旧入口,不划算。

**渗漏卡的撕裂标题与 `fusionFlicker*` CSS 全部保留**,复用为揉合结果卡的形态 ——
彩蛋不丢,丢的只是触发方式。这正是本 ADR 的一句话总结在资产层面的体现(见下)。

### 8. 融合封面与 host 色板的边界过渡(挂 B2-局内,本轮不做)

刀 2 记的色温对照组观察(识海遗蜕暖金封面 × 金光皮肤 vs 守则即补给暖锈封面 × 冷蓝皮肤)
指向的处理口径是:**修边界不迁就主色** —— 不让 host 色板向封面偏,
否则 foreign 还没渗漏、host 自己先被稀释了。

### 关键理由

1. **复用的是形式,变化的是解释。** 这一句是可组合模型的一句话总结:
   五拍骨架、渗漏卡形态、材质槽位都是复用的形式;哪两套材质同台、host 是谁、
   签名怎么渗,是每次不同的解释。加一个世界只加解释,不加形式。
2. **成本结构与 F-016 同形**:资产 N、覆盖 O(N²),per-combo 只需登记文案。
3. **只读投影与 severity 契约同族**:语义产出方在掌握语义的那一层,消费方无知。
4. **入口 / 局内两分**,让「强视觉」与「可持续阅读」不必互相妥协——
   这是四刀反复踩过的那条线(F-019 承载面、ADR-018 §4.12)在融合场景的应用。

## 已知代价

1. **后端不再是零动**:多了一个只读投影(registry 一个只读方法 + 控制器响应加一个 key)。
   缓解方式:改动性质写死为只读投影,不进 state schema、不进 wire 校验、引擎绝不读;
   `schemaVersion` 保 "0.4" 可作为「没有语义扩张」的客观检查点。
2. ~~**四套物理各调各的**~~(2026-11-05 四套物理已退役,本条随之失效;现行代价见文末「订正」§9):代码量与调参成本高于统一动画,且四套之间没有共享的正确性保证——
   某一套调坏了只能靠真机看出来。缓解方式:五拍骨架与时长表是**单点**,
   四套物理只在「碎解拍 / 揉合拍怎么走」两个函数里分派。
3. **入口强视觉与局内克制的边界靠纪律守,不靠机制**:没有任何代码阻止后来者把碎解搬进游戏屏。
   缓解方式:本 ADR §1 表格 + AGENTS.md Motion Constraints 的动效预算,
   以及「一世界一记忆点」护栏——融合局若再加一个强效果,预算表上立刻显形。
4. **误入手势彩蛋消失**:「摩挲卡片察觉异样」这个已上线的发现感被换成了「亲手撞」。
   这是有意识的交换:B1 结论表明拖拽能给到「亲手把两个世界撞在一起」的物理感,
   而那正是新入口相对旧入口的全部增量。视觉资产(渗漏卡)保留,只换触发方式。
5. **渗漏签名本轮只有约束、没有实现**:六条约束在真正做之前没有被任何代码检验,
   有「立字时看着对、实现时发现约束 2 太紧」的风险。缓解方式:B2-局内开工时
   第一件事就是拿四个世界的记忆点逐一对照这六条,不通过就回头改本 ADR 而不是绕过它。

## 重新审视的触发条件

- **世界数超过 6 个**:资产 N / 组合 O(N²) 的成本模型仍成立,但「四套材质」要变成「N 套材质」,
  届时复核是否需要材质分族(例如「硬边族 / 弥散族」)以免每个新世界都要从零设计一套碎解。
- **B2-局内实现时六条约束中任一条被证明过紧或过松** —— 回头改本 ADR §4,不在实现层绕过。

## 挂账

### 融合入口的视觉焦点管理(2026-08-05 真机冒烟提出,下一轮)

> ⚠️ **作废(2026-11-09;上文原文不动)**:本条挂账不再做 —— 入口没有动作,「把动作组织成一个事件」的问题随之不存在。见文末「订正(2026-11-09):入口去动画」。

**症状**:五拍演完了、四套物理各走各的、材质也确实在碎,但玩家读到的是
「一组碎片特效在列表中间播了一下」,而不是「两个世界撞在一起、新世界诞生」。

**四条根因(如实记,不是四条改进建议)**:

**a. 没有视觉焦点。** 碎片漂在页面空白处像**装饰层**,不像被某个力量吸引。
所有运动必须指向同一个中心:**卡靠近中心 → 碎片飞向中心 → 世界核在中心形成 →
新卡从中心展开**。现在**这条链是断的** —— 碎片与世界核在代码上都对着同一个坐标,
但在观感上不属于同一个「事件」。

**b. 融合卡仍是普通列表卡。** 揉完只是「又多了两个矩形选项」。
新卡应当**从世界核展开**,而不是插入列表。

**c. 画面没有主次。** 融合时其他卡应临时降低存在感,让融合区成为唯一焦点;
现在原卡、新卡、碎片同时醒目。

**d. 工作顺序错了:静态构图未定就在调动画。**
与 §4.12(搬元素要连关系一起搬)、§4.8(承载表面)、修仙屏色温断裂**同族** ——
**都是「关系没定就调元素」**。
> **开刀口径立字:下一轮先回样板间定静态构图,冻结后再碰 GSAP 时间线。**

**方向已定(不必再发散)**——「B 的焦点管理 + C 的改动范围」:

- 页面**不永久变暗**,只在融合那一秒形成**局部仪式空间**(两卡之间约 120–180px)
  + 短暂降低其他卡存在感;
- **世界核 48–72px**(现为 22px),它是**过渡状态不是常驻组件**;
- 新卡完成后**所有特效 0.5–1s 内静止**。

**明确不做**:全屏粒子爆炸 / 宇宙漩涡 / 3D 卡牌 / WebGL·Three.js·Canvas 粒子引擎 /
Rive / Lottie / Figma 流程(**样板间已承担静态先行的角色,不引新工具**)。

> 与 **B2-局内(§4 渗漏签名六条约束)** 相互独立,两条各走各的轮次。

### 融合方向的可发现性(2026-08-07 正式发布真机反馈,**与视觉焦点管理同批做,不单独开轮**)

**反馈原文**:「末日 → 规则怪谈可以、规则怪谈 → 修仙可以,反过来就不行。」

**先立字:这是设计正确的行为,不是 bug。** 后端 `FUSION_COMBOS` 只登记两对,
且**方向写死**(§5:被拖者 = foreign、承接者 = host);**反向组合是另一个尚不存在的融合世界**,
不是把现有那个免费翻转过来 —— 「修仙 × 规则怪谈」的 host 是修仙(识海遗蜕),
反过来要求的是一个以规则怪谈为 host、修仙为渗漏的**新世界**:新的 worldview 融合、
新的轴合并结果、新的守则形态、新的结局设计。**它得被写出来才能存在。**

**真正的缺陷在可发现性,不在方向语义**:玩家**靠试错**才知道该往哪边拖;
而反向被拒时只有一句「两个世界尚无法彼此容纳」——**那句话是给「这对组合不存在」准备的,
不是给「你拖反了」准备的**。同一句话在两种截然不同的情形下出现,玩家无从区分
「这两个世界永远不能融」与「顺序反了,换个方向就行」。

**两条候选处置**:

- **a. 区分两种拒绝提示**:「这对组合不存在」vs「试试反过来拖」。
  数据已经够了 —— `GET /api/archetypes` 的 `fusions` 只读投影里能查到反向是否登记,
  **纯前端判一下即可,后端零动**。
- **b.(倾向)磁吸时给方向提示**:靠近目标卡、尚未松手时显示
  **「将『规则怪谈』揉入『修仙』」**,玩家在**松手之前**就知道会发生什么。
  Felix 原设计里本就写过这条。

**倾向 b 的理由**:它在**动作发生之前**给信息,a 是**事后补救**。
b 顺带解决的是同一个根 —— 方向语义(谁是 host)本来就只存在于玩家脑子里的推断中,
把它**在拖拽过程中显式说出来**,方向就不再需要试错去发现。
(两者不互斥:b 做了之后 a 仍有价值 —— 真·不存在的组合还是要给一句像样的话。)

**为什么与视觉焦点管理同批**:两者都动**拖拽进行中的那一段呈现**(磁吸态、目标高亮、
仪式空间的建立),分两轮做会把同一段时间线改两次;且 b 的提示文字**落在哪、多大、什么时候出现**,
本身就是「静态构图冻结」要回答的问题之一。

### 待决(不做,只记):入口范式是否退回长按误入(2026-08-06)

**观察(Felix)**:两种入口给的是**不同的情绪**,不是好坏之分 ——

- **长按误入**的核心体验是「**不小心摸到了不该存在的东西**」,惊喜来自**意外**;
- **拖拽**是「**我主动制造了一个新世界**」,满足来自**创造**。

**当前状态**:拖拽版真机观感未达预期,但**动画尚未按新构图重做** ——
**现在比较的是半成品与成品**,此刻下结论不成立。

**决策条件**:等动画按上面那张冻结构图重做之后再判。
若届时仍觉长按更好,**退回是有依据的选择** —— 但要明确知道这是在
**用创造感换意外感**,而不是「拖拽做失败了所以退回去」。

**回退成本(如实记,免得被当成一个开关)**:长按状态机(`FUSION_GESTURES` /
`nextFusionStages` / 600ms 长按)**已于 `cf28d6f` 退役删除**,退回是**实打实的工作量**;
且 §7 记的那条技术事实不因此改变(180ms 抓起是 600ms 长按的真子集,两者不能真正并存,
退回意味着**拖拽入口整体下线**,不是两个入口并存)。
**渗漏卡视觉资产全部保留**,退回时不需要重做视觉。

## 实施记录

### 刀 1 · 融合方向提示 + 拒绝提示就近(2026-10-19,基于 `ffde1bd`)

上文「方向可发现性」挂账的 **a、b 两条一起落地**(两者本就不互斥)。**范围只到提示与文案** ——
五拍揉合时间线、磁吸 / 排斥位移、阈值一概未动(那是刀 2 的事)。

**1. `classifyPair` 三态(`web/src/features/game/fusion/drag.ts`)**

`classifyPair(fusions, host, foreign): 'ok' | 'reversed' | 'none'`:

- `ok` = (host, foreign) 本身已登记;
- `reversed` = (host, foreign) 未登记、但 (foreign, host) 已登记 —— 玩家拖反了;
- `none` = 两个方向都未登记(含同一张、空组合表)。

它**只给提示分支用**。合法性判定仍只认 `isFusionAllowed`(语义未改):手势层吸不吸、提不提交不看 `classifyPair`。
单测钉了「`ok` ⇔ `isFusionAllowed` 为真」对四个世界全部 16 对成立。

**2. 三句文案(Felix 定稿,`fusion/hints.ts`,一字不改)与时机**

| 三态 | 何时出 | 文案 |
|---|---|---|
| `ok` | 吸附到合法目标约 150ms 后淡入,进入可提交态时加强(字色 / 边框转亮,不加位移) | 「将『{来源}』揉入『{承接}』。」 |
| `reversed` | **悬停时不出**,松手才出 | 「反过来试试:把『{来源}』拖到『{承接}』上。」 |
| `none` | 悬停时不出,松手才出 | 「两个世界尚无法彼此容纳。」 |

填名:来源 = 合法方向里被拖的那张(foreign),承接 = host;拖反时填**合法方向**的名字,即把这次拖动的两张对调。
世界名取卡片标题(`displayName`),不用 id。

**3. 位置体系(磁吸与拒绝共用)**

- 原页头 `.fusionNote` 那行静态字删去,`ArchetypeSelect` 里写死的字符串改走 `classifyPair` 分支。
  **动效预算**:提示属于用户触发槽,**替代**页头那行静态提示,不是新增效果;淡入一次即止,不循环。
- 提示相对 `.cardList`(新增 `position: relative`)绝对定位,竖直居中在**目标卡上沿或下沿外的卡间缝**里:
  `top` 在提示挂上 DOM 时(ref 回调)按目标卡 `offsetTop` / `offsetHeight` 写一次,再用 ±半缝(0.425rem)推进缝中。
  缝 + 邻卡内边距 > 提示高度,压到的只有邻卡内边距,**不压任何一张卡的标题**。`pointer-events: none`,z-index 高于抓起的卡。
- **放哪一侧**:
  - 磁吸:**与拖动卡来的方向相反** —— 拖动卡中心在目标中心之上 → 放下沿外,反之放上沿外。
    两张卡的标题都在各自顶部,这样两边都不被压住。侧位在命中新目标那一刻定下,同一目标内不翻面
    (`useFusionDrag` 的 view 新增 `targetSide`)。
  - 拒绝:松手后被拖的卡正往原位回弹 → 放在它**不经过**的一侧(被拖卡原位在目标之上 → 放下沿外,反之上沿外)。
- 提示消失时淡出(元素留到下一条提示替换它);换目标 = 换一条提示 = 重新淡入。
- 拒绝提示在**下一次抓起**或成功揉合时散去(原口径是「下一次成功手势即散」;改成抓起即散,是因为下一次拖动会在别处出磁吸提示,同屏只留一条)。
- reduced-motion:淡入动画换成纯 opacity 关键帧,**不位移**;淡出本来就只有 opacity。

**4. 无障碍:一个 aria-live 区,只在文本变化时写入**

- 页头里放一个始终在场的 `aria-live="polite"` 区(视觉隐藏),三类提示**只经它播报**;视觉提示本身 `aria-hidden`,不重复念。
- 由 `announce(text)` **直接写 DOM**,写之前与本次手势里最后写入的文本比对,**相同就不写**:
  - 同一次拖动里离开目标、再回到同一目标 → 文本没变 → 不写 → 不重播;
  - 换到另一个合法目标 → 文本变了 → 写;
  - 悬停在拖反 / 不存在的目标上 → 没有磁吸文本 → 不写;
  - **离开目标时不清空**播报区(清空再写回同一句就是重播);
  - **抓起新的一张时**(`useFusionDrag` 新增 `onPickUp`)清空播报区并重置比对基准 —— 所以下一次手势回到同一目标会重新播报一次。
- **验证方法(写入计数)**:组件测试 `ArchetypeSelect.hints.test.tsx` 给播报区的 `textContent` setter 包了一层计数,
  断言「同一手势内 进→出→进→出→进 同一目标」非空写入恰为 1 次、下一次手势回到同一目标再 +1、悬停非法目标 0 次;

**5. 三项勘察结论(简报第 3 条)**

- **`nth-child` 入场错峰**:不受影响。`.cardList .card:nth-child(1–3)` 只给 `cardEnter` 设 `animation-delay`,
  插入成品卡会让其后的卡换 `nth-child` 序号,但它们的 `cardEnter` 早已播完,改 delay 不会重播(动画名没变);
  成品卡自己的入场是 `none`,序号对它无效。方向提示仍放在列表末尾,不占序号。
- **磁吸提示的定位(`.cardList` 锚点)**:不受影响。提示的 `top` 在挂上 DOM 时按目标卡 `offsetTop` 量一次,`offsetTop` 不含 transform,
  插入后再出现的提示按新布局量;揉合期间手势锁住,不会有新提示。揉合开始时淡出中的那条提示 `top` 已过期,但它在淡出、看不见。
- **焦点管理(`focusOnMount`)**:**会被打乱,已改**。成品卡现在在揉合**开始**就挂载,若仍在挂载时聚焦,浏览器会按它的**最终**布局位置滚动,
  而画面上它还叠在宿主卡位上。改为揉合演完(或兜底放行)才 `setFocusKey`,`FusionCard` 的聚焦 effect 依旧只此一次。

修法(只作用于揉合期间的成品卡,不改全列表卡片高度,不截断、不缩放任何文字):

- 成品卡在宿主卡位里时,布局 `min-height` 钉成宿主高度(在量 FLIP 之前钉,下面的卡按钉后的布局抵消),外边界与宿主卡逐像素重合;

  下面的卡同步多走这段差;收完那一帧撤钉高、撤裁切、下面的卡 `y` 归 0,三者互相抵消;
- reduced-motion:本就不移动,文字到齐那一刻连同高度差一起直接就位,不裁切。

- **量取改为亚像素**:原先用 `offsetTop` / `offsetHeight`,它们取整,而卡列是小数布局(卡间缝 13.6px),

**8. 返工:松手时被拖卡跳回原位(校勘用真实鼠标事件复现,2026-11-05)**

- **事实订正**:上文第 6 条说「录屏抓到两处真缺陷,已修并补单测」—— 修是修了,但那两段录屏和单测都**没走真实路径**:
  录屏用的是页面假时钟,单测在 jsdom 里。另外,当时把假时钟下「被拖卡的 transform 被冻住」判成录屏工具的问题,**这个判断是错的**:
  卡片自带 `transition: transform .12s`,拖动时屏上位置本来就落后内联值,那是真实行为,见下面的根因 2。
- **根因 1(跳回原位)**:`FusionMerge` 的 effect 不幂等。被拖卡的松手姿态只存在于内联样式里,而 effect 的清理会清掉全部内联样式。
  React StrictMode(dev 构建)会让 effect 先挂载、清理、再挂载,第二次运行时被拖卡已经回到自己的卡位,于是在原位淡出。
  真时钟 + 真鼠标实测:dev 服务器上松手后 15ms 内跳回,480 宽克苏鲁位移 105px,375 宽人防 119px,reduced 下相同。
  生产构建里用同样的手势**没有复现**这一条(effect 只运行一次)。
- **根因 2(往前跳,仅快速松手)**:手势层冻结的是内联**目标值**,不是屏上位置。快速拖到就松手时,屏上位置还在 .12s 过渡途中;
  揉合一量布局、一关过渡,卡就往前跳到目标值(生产构建实测 480 宽约 60–80px)。
- **修法**:提交时把被拖卡的**屏上** computed transform 冻结成内联值并关掉过渡,连同层级作为 `CommitCards.pose` 交出去;
  `FusionMerge` 的 effect 每次开始时都按 `pose` 重摆被拖卡。StrictMode 下的第二次运行也就从松手姿态开始。
- **回归**:jsdom 里 `<StrictMode>` 会重复调用 effect,能抓到根因 1(`FusionMerge.test` / `ArchetypeSelect.fusion.test` 新增的 StrictMode 用例,
  在旧代码上失败)。根因 2 涉及 CSS 过渡,jsdom 抓不到,另写了真实时序脚本 `web/dev/fusion-release-check.cjs`:
  真时钟 + 真鼠标,每个 rAF 读被拖卡的 `getBoundingClientRect`,覆盖 480 宽三对 + 375 宽人防正常 / reduced,每种两类手势(停留后松手 / 到了立刻松手),
  共 10 个用例。旧代码在 dev 服务器上 10 个全部失败;修复后 dev 服务器与生产构建(`vite preview`)各 10 个全部通过,松手那一帧位移 0.0px。
- 验收录屏改为真时钟、真鼠标(CDP screencast 按真实帧时间戳抓帧,生产构建),480 宽三对 + 375 宽人防正常 / reduced,随交付说明发出,未入库。

| 场合 | 今天会不会播 | 处置 |
|---|---|---|
| 揉合演完(`onMergeDone` → `revealFusion`),三对组合 | 播 | **拿掉**:揭晓或交叉淡化结束时,成品卡已经在最终位置和尺寸,再竖向展开一次就是重复入场,而且整卡模糊违反 §2 通用禁令 |
| 兜底:量不到位置(`onCommit` 里 `!rects`,不演动画、直接给卡) | 播(这里唯一的入场) | **建议拿掉,卡直接出现**,理由同上(整卡模糊)。这是本订正的提议,Felix 未单独裁定,生产刀动手前确认 |
| 页面重新挂载(离开选择屏再回来) | **不播** | 不涉及:`fused` 是组件内 state、零持久化,回来时没有融合卡 |
| 同一组合再揉一次 | **不播** | 不涉及:`revealFusion` 去重,已有的卡不会重新挂载 |
| reduced-motion | 不播(已关) | 不变:减弱动效块里的 `.card:not(.cardLocked)` 与 `.card.cardFusion*` 特异性相同且写在后面,`animation: none` 生效 |

结论:两条挂载路径都拿掉之后,`@keyframes fusionSeep` 在生产里就没有使用者了,生产刀里可以一并删掉。

### 9. 已知代价(照实写)

## 订正(2026-11-09):入口去动画

### 1. 裁定
