**Felix 已定(2026-11-20)**,本 ADR 不再讨论,只照写:

1. **结构**:选择屏顶部标签「浮世 · 深界 · 渗界」,只能点、不能左右滑(横向手势归融合拖拽,ADR-018 §4.20)。
   标题与「我的存档」「回看上局」在标签上面,不随切区变。新玩家默认浮世,之后记住上次停的区。
   这对应世界目录第二节 (4) 的 **C「一个大厅 + 顶部分区」**,但没有「全部」那一格。
2. **渗界一开始隐藏**:只有「浮世 · 深界」两个标签。只有深界的卡能拖,浮世只能点。
   第一次合成成功 → 第三个标签出现(**甲**:「渗界」两字一起淡出 700ms;前两个标签平移让位 600ms;合成后停 900ms 再出现;页面停在深界)。
   **这一下一辈子只发生一次,是大厅的一级记忆点。**渗界里放已发现的融合世界,点卡直接开局。
3. **跨区融合不堵死**(世界目录立字四 / 七):现有三个融合组合的参与世界都在深界;将来有跨区组合时在渗界加「合成台」。本 ADR 只写成约束。
4. **三区页面**:卡片原样不动;只改页面底色、文字色、卡片间距、页头留白;切区 400ms 只淡底色与文字色。数值见样张 `.zFushi / .zShen / .zRong`。
5. **背景气氛层**(卡片后面,只从卡缝、页头、页边露出):浮世 = 淡暖色 + 四道斜照暖光;深界 = 约 9s 一次远处闪电;
   渗界 = 更淡的暖光偶尔发暗 + 往暗紫里闪的远雷。reduced-motion:光静止,闪电不出现。
6. **文案**(1A 2A 3A 4B 5B):第三区「渗界」;浮世副标题「每一个世界都由 AI 即时生成,烟火寻常,慢慢过活。」;
   深界副标题原句不动;渗界副标题「两个世界渗在一起,就不再是原来任何一个。」;深界暗示句「别把两个世界放得太近。」;
   渗界底句「还有别的世界,正在深界里互相渗着。」。

约束条件:

1. **立字一不变**:分区只在大厅成立,进局之后视觉真理源仍是世界自己的主题注册表(ADR-018 §4.1)。游戏屏 DOM 与计算样式一律不动。
2. **不动融合拖拽手势本身**(`useFusionDrag` 的判据与阈值)、**不动 ADR-019 冻结构图**、不做 ARCHIVE 档案形态(世界目录立字六)、不做合成台。
3. **不改任何世界的卡面 CSS**。
4. 不动 state schema、不动 Engine;`schemaVersion` 仍 `"0.4"`。`GET /api/archetypes` 多一个字段属 CONTEXT §三.15 的端点契约,**实施时回写 CONTEXT**,本草案不改。

### 勘察结论(只读 `main` `8a75ce5`,2026-11-20)

**A. 选择屏现状**(`web/src/features/game/ArchetypeSelect.tsx`)

- `<main>` 的子结构:`header`(含唯一的 aria-live 播报区)→ 有存档时 `SaveList` 的 `<section>` → 探测成功时「回看上局」`<button>` → `.cardList`。
  卡列顺序 = 已开放卡(全部可拖)→ 本次揉出的融合卡(`fused`)→ 未开放卡 → 方向提示。
- `fused` 是**纯组件 state**,注释原话「零持久化 —— 离开选择屏即遗忘」;刷新即丢。
- 合成成功:`onCommit` 追加 `fused`、发 `focusReq`(成品卡挂上即获得焦点)、播报「融合成功。《X》已加入世界列表。」(Felix 2026-11-09 定稿)。
  成品卡带 `fresh`(`.cardFresh`,标题先停在真名 5.2s)。
- 选择屏没有任何页面级动效;卡片各有自己的循环环境动效(`::before / ::after`),规则怪谈卡另有「偶发冷光闪烁」。
  融合入场动画已于 ADR-019 订正(2026-11-09)整体撤掉 —— **选择屏现在没有一级记忆点**。
  ADR-019 订正 §7:「将来若要给入口重新加动作,按『新增动效』处理,先另记 ADR」—— 本 ADR 就是那一份。

**B. 卡面对页面令牌的依赖**(决定「卡片原样不动」能不能字面成立)

逐条读了 11 张卡的主题块(8 个单体 + 3 个融合):各卡都覆盖了 `background`(不透明)、`color`、`border-left-color`,
标签与标语各有 `.cardX .cardTag / .cardTagline` 覆盖。**仍读页面令牌的只剩一处**:
`.card { border: 1px solid var(--line) }` 的上、右、下三边。所以页面令牌换成三区那套之后,**每张卡的 1px 外框颜色会变**:

| | 线上(系统浅色) | 线上(系统深色) | 浮世 | 深界 | 渗界 |
|---|---|---|---|---|---|
| `--line` | `#e5e4e7` | `#2b2733` | `#ddd5c8` | `#2a2730` | `#9d97a5` |

样张里卡片就是这样(真实 CSS + 区令牌),Felix 看到的效果已包含这一变化。
另外拖拽态 `.cardTargetValid`(`--accent`)、`.cardTargetInvalid`(`--line`)与方向提示 `.fusionNote`
(`--card / --line / --muted / --text / --accent`)也读页面令牌;它们只出现在深界,跟随深界令牌。
→ 见决策 4 与待审 1。

**C. 卡片间距与方向提示的半缝**

`.cardList { gap: 0.85rem }` 的注释:「改它要同步 `.fusionNote` 的半缝偏移 0.425rem」。三区间距为 1.2 / 0.6 / 0.9rem;
方向提示只在深界出现,深界的半缝应为 **0.3rem**。样张没有方向提示,这个数是按现有注释推出来的。

**D. 切区时卡片会重新挂载**

各区卡片不同,切区即换一批卡挂上,`.card:not(.cardLocked)` 的入场动画 `cardEnter`(0.5s,淡入 + 上移 8px,前三张错峰)会再播一次。
样张用 `innerHTML` 换卡,同样会重播 —— 样张里看到的切区就带着这一下。而「切区只淡底色与文字色」字面上不含它。→ 待审 3。

样张另有 `.lb .selectHeader { transition: padding 0.4s ease }`:动画化 `padding` 违反 Motion Constraints §6(避免动画化布局属性),
也不在「只淡底色与文字色」之内。→ 决策 5 不照搬。

**E. 数据来源**

- 服务端 `ArchetypeMeta`(record)现有 `tagline / vibeTag` 两个「只供选择屏」的字段,经 `ArchetypeRegistry.listForSelection()` →
  `ArchetypeSummary` → `GET /api/archetypes` 下发。registry 里**没有**任何体验分类字段(`experienceMode` 全仓 0 处)。
- `new ArchetypeMeta(...)`:`ArchetypeRegistry` 8 处、测试 1 处(`FixedWorldTitleTest`)。另有一个不带 `fixedWorldTitle` 的 8 参便捷构造器。
- 未开放占位表 `INACTIVE_DISPLAY_NAMES` 是 `Map<String,String>`(id → 中文名),现为空表,分支刻意保留(ADR-036 裁定 4(a)),
  测试经 `FakePlaceholderRegistry` 注入假占位。
- 前端单一主题注册表 `theme/registry.ts` 只管封面、卡皮肤、局内皮肤,不管分类。
- 前端与后端同一个镜像发布(Dockerfile 三阶段,`web/dist` 拷进 Spring `static/`),不存在「新前端配旧后端」的线上窗口。

**F. 存档能不能看出融合局**

`SaveSummary.archetypes`:「单体一个;融合为 host 在前的有序对。迁移来的旧指针为空数组。」→ **能**:长度 2 即融合局,
`fusionKey(a[0], a[1])` 即组合键。空数组的旧指针在首次续局成功前看不出来。

**G. 浏览器存储的现有边界**

`savePointers.test.ts` 有两条源码级断言:存档键字面量 `aiuniverse.save` 只出现在 `savePointers.ts`;
**调用 `localStorage` 的只有 `savePointers.ts` 与 `api/deviceId.ts`**。新增一个存储模块必须改这条断言的白名单。
eslint 的 ADR-003 边界只禁 `fetch / EventSource / WebSocket / XMLHttpRequest / wx`,不禁 `localStorage`(`state/savePointers.ts` 即先例)。

**H. 主题与明暗**

`index.css` 的 `:root` 页面令牌跟随 `prefers-color-scheme`;选择屏没有主题根,所以现在跟随系统深浅色。
游戏屏按 ADR-018 §4.6「世界决定明暗」由各世界皮肤的主题根 + `position: fixed; inset: 0` 铺底层决定,不跟系统。

## 候选方案

本 ADR 有两处真正要选的:**分区归属从哪来**、**「已发现」记在哪**。其余是照样张落地的细节,写在最终决策里。

### 归属来源 · 方案 A:前端登记表(加在 `theme/registry.ts` 的 `WORLDS` 上)

**优点**:
- 后端零改动,CONTEXT §三.15 不动。
- 分区是纯大厅展示,和卡皮肤登记在一处。

**缺点**:
- **两个真理源**:世界目录由后端下发(§三.15「不让前端硬编码模式清单」),归属却在前端;后端新激活一个世界而前端没登记,
  前端只能猜一个缺省区。这正是 ADR-019 方案 1 否掉「前端自备组合表」的同一形状(「双真相源会漂移」)。
- 世界目录立字五「每个新世界**登记时**都须回答属于哪一侧」—— 登记动作发生在后端 `register(...)`,
  前端登记表漏答只能靠「后端目录 ⊆ 前端表」的跨端测试兜,而前端测试拿不到后端真实目录。

### 归属来源 · 方案 B:后端 `ArchetypeMeta` 加必填字段,经 `GET /api/archetypes` 下发(本 ADR 采纳)

**优点**:
- 登记即回答:字段进 record 的规范构造器、便捷构造器不给缺省值 → **漏答编译不过**;再加非空断言与目录测试,三层兜底。
- 与 `tagline / vibeTag` 同一先例:只供选择屏的玩家无关元数据,不进 world-gen 注入,不进局内(立字一不变)。
- 前端只消费,不判世界(ADR-018 §4.1「世界判定只发生一次」)。

**缺点**:
- 端点契约多一个字段,CONTEXT §三.15 要回写;9 处构造调用都要改一遍。
- 占位表从 `Map<String,String>` 改为带分区的形状,`FakePlaceholderRegistry` 跟着改。

### 「已发现」· 方案 1:只记浏览器

**优点**:简单;Felix 定的默认。
**缺点**:清掉站点数据、换设备、隐私模式即丢;老玩家已经玩过的融合局不算数。

### 「已发现」· 方案 2:浏览器记录 ∪ 存档推导(本 ADR 采纳)

**优点**:
- 玩过融合局的老玩家,上线后第一次进大厅就能看到渗界(存档指针里已有有序对)。
- 存档指针本来就在本机,不新增网络请求。

**缺点**:
- 推导结果和浏览器记录都依赖同一个 `localStorage`;存储不可用时两者一起失效,当作「没发现」。

### 「已发现」· 方案 3:服务端记录

**否决**:要按设备记一份玩家状态,等于在 ADR-034「指针只在客户端」之外新开一条持久化路径;为一个大厅标签不值得。

## 最终决策

**方案 B + 方案 2**,其余照样张落地。

### 1. 分区归属:`ArchetypeMeta` 加必填 `experienceMode`

- 后端:`ArchetypeMeta` 新增 record 组件 `ExperienceMode experienceMode`(枚举 `FUSHI` / `SHENJIE`),
  紧凑构造器 `Objects.requireNonNull`;8 参便捷构造器**也**加这一参数,不给缺省值。
  八个已激活世界按[世界目录](../world-catalog-and-experience-modes.md)「三区计数(截至 `080494f`)」填:
  浮世 = `life_sim` / `animal_life` / `time_travel`;深界 = `cyberpunk` / `cultivation` / `rules_creepy` / `apocalypse` / `cthulhu`。
- 占位表 `INACTIVE_DISPLAY_NAMES` 改为带分区的条目(id → 中文名 + 分区);未开放卡也必须回答属于哪一侧。
- `ArchetypeSummary` 加 `experienceMode`,JSON 值为小写 `"fushi"` / `"shenjie"`(键名、取值待审 5)。
- **融合世界不加字段**:按立字七一律进渗界,前端据 `fusions` 只读投影即可,后端不重复声明。
- **让漏答变红**(世界目录立字五):
  1. 编译期 —— 两个构造器都要求该参数;
  2. 运行期 —— 紧凑构造器非空断言;
  3. 测试 —— `ArchetypeRegistryTest` 加一条:`listForSelection()` 每一项(含 `FakePlaceholderRegistry` 注入的占位)`experienceMode` 非空;
     `ArchetypeControllerTest` 加一条:JSON 里每张卡都有这个键;
  4. 跨区守卫(决策 7)—— `FUSION_COMBOS` 每一项的两个参与世界都必须是深界,否则测试失败,失败信息指向本 ADR 决策 7。
- 前端 `ArchetypeSummary` 类型加 `experienceMode: 'fushi' | 'shenjie'`。`h5GameApi` 对缺这个键的卡(测试替身、老后端)按**深界**处理 ——
  那是合成前所有卡所在的行为(可拖),不会让任何卡变得不能玩。线上前后端同镜像,这条只服务测试与本地桩。

### 2. 「已发现」与「上次停的区」

新增一个只碰大厅键的存储模块(暂名 `web/src/state/lobbyPrefs.ts`),全部读写 try/catch,读不到就当没有:

| 键(暂定) | 值 | 写入时机 |
|---|---|---|
| `aiuniverse.lobby.zone` | `"fushi" \| "shen" \| "rong"` 之一(同样张的 `data-zone`;深界、渗界拼音都是 shenjie,所以不用全拼) | 每次切区 |
| `aiuniverse.lobby.discovered` | 组合键数组,按发现先后 | 合成成功(`onCommit`)当下 |
| `aiuniverse.lobby.revealed` | `true` | 第三区出现动画**开演那一刻**(决策 6) |

- 键名不得含 `aiuniverse.save`(不碰存档键断言);`savePointers.test.ts`「调用 `localStorage` 的只有……」白名单加这一个文件。
- **已发现集合** = 浏览器记录 ∪ 存档推导(`saves` 里 `archetypes.length === 2` 的 `fusionKey`)∩ `fusions` 投影里的键 ∩ 前端有卡文案的键。
  取交集是为了:后端撤掉一个组合、或前端还没配卡文案时,渗界里不出现一张点了会 400 或渲染不出的卡。
- **渗界标签可见** ⇔ 已发现集合非空。
- **初始区**:读到存储且合法 → 用它;存的是渗界但已发现集合为空 → 浮世;读不到 → 浮世(Felix 定「新玩家默认浮世」)。
  老玩家第一次进新大厅也落在浮世 → 待审 4。
- 跨页签:沿 `onSavePointersChanged` 的先例,另一个页签写了大厅键时刷新已发现集合;不在本页签播第三区出现动画。

### 3. 结构与无障碍(标签)

DOM(`<main>` 的直接子元素):

```
header(标题 / 副标题 / 播报区)
section 我的存档            ← 有存档时
button 回看上局              ← 探测成功时
div role=tablist aria-label="分区"
  button role=tab #lobby-tab-fushi   浮世
  button role=tab #lobby-tab-shen    深界
  button role=tab #lobby-tab-rong    渗界   ← 未发现时不渲染
div role=tabpanel aria-labelledby=<当前标签 id>
  p 深界暗示句                ← 只在深界
  div .cardList
  p 渗界底句                  ← 只在渗界(待审 6)
```

- 副标题在 header 里但**随区换句**(样张 `#sub`);标题、存档、回看上局位置与内容不随区变。颜色跟随区令牌(样张如此)。
- 只渲染一个 tabpanel,换区即换内容,`aria-labelledby` 跟着换。不用 `hidden="until-found"`(没有隐藏面板)。
- 标签用 `<button type="button">`;不加 `aria-controls`。用 `div` 而不是样张的 `nav`:这是页内分区,不是导航地标。
- **键盘**:roving tabindex(选中的标签 `tabindex=0`,其余 `-1`);←/→ 在可见标签间移动焦点并循环,Home / End 到两端;
  **Enter / Space 才切区**(selection by activation)。理由:切区会写存储、整列换卡并重播入场、页面高度大变 ——
  参考指南自己把这三种情况列为「改用 activation」的条件。→ 待审 7。
- **选中态**:不只靠颜色,用一道 2px 下划线(样张)。实现改为 `::after` 上的 `border-block-end`,视觉与样张逐像素相同:
  样张给每个标签都挂 `border-bottom: 2px solid transparent`,强制颜色模式下透明边框会被系统色画出来,所有标签都会带下划线,选中态就没了。
- **热区**:`min-height: 44px`(样张);宽度由两个字 + 字距撑起,按 0.95rem 估约 46px,贴着下限 —— 实施时按 ADR-018 §4.18 的方法实测
  (以标签中心取 44×44 正方形,9×9 网格逐点 `elementFromPoint`,三个标签都要 81/81),不够就加左右 padding 并请 Felix 看。
- **不能滑**:标签条与面板都不挂任何横向滑动处理;深界卡仍是 `touch-action: pan-y`(ADR-018 §4.20(a))。
- 第三个标签出现时**不抢焦点**:焦点留在刚挂上的成品卡上(现有 `focusSignal` 行为)。
- 参考:`modern-web-guidance@1.0.0`(`npx -y modern-web-guidance@1.0.0 retrieve tabs`,2026-11-20 取)。只作参考,与本项目冲突处以本 ADR 为准:
  - 不用 `focusgroup`:指南写明只有 Chrome / Edge 150 支持,其余要加 `@microsoft/focusgroup-polyfill`,那是新的 npm 依赖;手写 roving tabindex 只多十几行。
  - 指南默认 selection follows focus;本 ADR 选 activation,理由见上,指南列出的例外条件正好命中。
  - 下划线用伪元素边框、不用 `box-shadow` / 背景、选中态不改尺寸、不加 `aria-controls`、标签单行 —— 照指南。

### 6. 第三区第一次出现(大厅的一级记忆点)

时间线(样张默认值,Felix 定「甲」与默认时长):

| 时刻(从松手提交算) | 发生什么 |
|---|---|
| 0 | 成品卡照现在挂在深界列表末尾(已开放卡之后、未开放卡之前),带 `.cardFresh`,获得焦点;播报一句(待审 2)。被拖卡走 260ms 回位过渡 |
| 0 | 写入已发现(决策 2)。已发现集合原本非空时到此为止,没有下面几行 |

### 9. 动效预算(Motion Constraints §2 / §3)

**照实写:区背景气氛是新增,它不替代任何东西,也没有降级任何东西。**选择屏此前没有任何页面级动效;卡片的环境动效是每张卡自己的。

逐区的槽位(页面层):

| 区 | 持续环境 | 低频偶发 | 用户触发 |
|---|---|---|---|
| 浮世 | 暖光(四道光的明暗 + 整层慢移,同一层,照修仙流云 + 微粒的先例合为一个槽) | 无 | 无 |
| 深界 | 无 | 远处闪电(整页亮两下 + 细折线,同一关键帧同时发生,一个事件) | 拖拽(抓起 / 磁吸 / 回位)与方向提示淡入 —— 既有 |
| 渗界 | 暖光(同浮世) | 发暗(11s)**与**暗紫闪(13s) —— **两个,且没有代码保证的互斥** | 无 |
| 深界(第一次合成) | | | 第三区出现(一级记忆点,见下) |

三个问题要 Felix 裁定:

1. **预算按什么单位数**:线上先例是「每张卡各自加了一个持续环境动效」(ADR-020 / ADR-021 2026-11-12 补充段),
   即卡面各算各的;本 ADR 提议**页面层另算一份预算**,与卡面并列。若按「每屏」硬算,深界一屏同时有规则怪谈卡的偶发冷光闪烁与远处闪电,

2. **渗界两个低频**:按 §2.1,两个低频要么由代码保证互斥并记作一个槽,要么去掉一个。11s 与 13s 两个周期互不对齐,隔一阵就会撞在同一秒里。
   提议:合成一个 13s 的周期,发暗与暗紫闪是同一事件的两拍(先发暗、紧接着闪),写在同一份关键帧里,预算表记一个槽并标注两种表现。

3. **第三区出现算一级记忆点**:AGENTS.md §1 的表是按世界列的,大厅不是世界。提议在表里加一行「大厅(选择屏)· **渗界出现**」,
   规则同世界:唯一、不得再加第二个。它占的是深界的用户触发槽:在 900ms 时开演,被拖卡的 260ms 回位早已结束,两者不重叠。
   方向提示在松手时已经淡出。

### 11. 主题:三区固定配色,不再跟随系统

- 大厅改为每区固定配色:浮世恒浅、深界恒深、渗界恒为中灰。这是把 ADR-018 §4.6「世界决定明暗」**延伸到大厅**:区决定明暗。
  §4.6 原文「未登记世界仍跟随系统偏好」说的是游戏屏,本 ADR 之后选择屏不再有「跟随系统」这一档。
- **对系统深色用户的影响**:今天他们进选择屏看到的是深底(`#131019`);之后新玩家默认落在浮世,是一整页暖浅色(`#f3efe7`),
  加上浮世的暖光。对在暗处玩、或因畏光开深色模式的玩家是一次明显的变亮。缓解:切到深界后会被记住;要不要让「系统深色 + 新玩家」默认深界 → 待审 4。
- 系统浅色用户切到深界看到深底,这是设计本意。
- 大厅根设 `color-scheme`(浮世 `light`、深界 `dark`、渗界 `light`),让其中的表单控件与焦点环跟着区走。页面滚动条属于根元素,不受影响 —— 已知代价 4。
- 立字一不变:进局之后交回世界皮肤;状态屏(载入、出错)与选择屏在同一个根里,跟随当前区。

### 关键理由

1. **分区归属跟着世界登记走**:登记处只有一个(后端 `register(...)`),让「回答属于哪一侧」成为构造器参数,是唯一能在编译期变红的做法。
2. **前端不判世界**:分区、卡皮肤、局内皮肤三者都由单一来源给出,前端只消费(ADR-018 §4.1、立字一)。
3. **一次性效果守卫记「已开演」**:直接复用 ADR-018 §4.9 的教训,而不是重新犯一次。
4. **跨区先写成红灯**:「不堵死」不是「先不管」—— 第一个跨区组合到来时测试会把人带到决策 7,而不是悄悄做出一个拖不出来的组合。
5. **样张为准,但不替 Felix 圆**:卡框颜色、切区重播入场、渗界对比度、渗界两个低频这四处,样张与 brief 的字面不一致,全部列为待审,没有自行调和。

## 已知代价

1. **卡片 1px 外框随区变色**(若待审 1 照样张):「卡片一个像素不改」只对卡片内部成立。缓解:外框本来就随系统深浅色变,玩家感知不到「原来的颜色」。
2. **系统深色玩家进门变亮**:新玩家默认浮世。缓解:记住上次的区;待审 4 可改默认。
3. **「一辈子只一次」是本机、本浏览器的一辈子**:清站点数据、换设备、隐私模式会再看到一次;存储写失败时也会再看到。
   反过来,存储读不到时渗界标签不出现(当作没发现),要重新合成一次。缓解:存档推导让玩过融合局的人不至于从零开始。
4. **页面滚动条不跟区走**:`color-scheme` 设在大厅根上,不影响根元素的滚动条;桌面端深界会配一条浅色滚动条。手机端是覆盖式滚动条,基本看不出。
5. **深界卡缝变窄(0.85 → 0.6rem)**:拖拽手感与方向提示位置都要真机复测;B1 / B2 的结论以卡片列表为单位,这次单位没变、间距变了。
6. **端点契约多一个字段**:CONTEXT §三.15、9 处构造调用、占位表形状都要改。
7. **渗界里的卡点了就开局,没有「再拖一次」的入口**:在深界拖同一对也能开局,两条路并存。
