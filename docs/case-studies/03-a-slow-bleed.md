# `catch (RuntimeException)` 的慢性失血

> **拦截深度**:审阅(读 diff)· **到过哪**:写进了 commit(`03bcbd3`),从未上线 · **玩家可见**:否
>
> 出处:[ADR-022](../adr/ADR-022-turn-admission-and-rejection-semantics.md) §「审阅抓到的两条,连在一起(Felix,2026-09-03)」;
> 修法 commit `6a62d95`。本文只转写与索引,裁定真理源在 ADR。

## 现象

`TurnAdmission.submit` 的形状是:占到名额 → `executor.execute(...)` 提交 →
若提交本身抛,就在容器线程上把名额**归还**。

而它当时的 catch 是这样写的(`git show 03bcbd3` 实测):

```java
} catch (RuntimeException e) {
    permits.release();
    throw e;
}
```

**同一个方法的 javadoc 里,上面几行逐字写着**:

> 池 `shutdown()` 之后(容器正在停)`execute` 会抛 `RejectedExecutionException`,
> **那一刻若不归还,名额永久丢失。**

**catch 比它自己的警告窄。**

`newCachedThreadPool` 起不出线程时抛的是 `OutOfMemoryError: unable to create native thread` ——
那是 `Error`,不是 `RuntimeException`。而它**正是本 ADR 背景里那个场景**:
512MB 容器、**线程栈在堆外**。

## ⚠️ 后果不是崩溃,是慢性失血

这一条是全篇的重心,也是它最容易被低估的地方。

`OutOfMemoryError: unable to create native thread` **不一定杀死 JVM** ——
堆可能完全健康、进程继续跑、玩家照常在玩。
于是**每漏一次,名额上限就少一个**:8 → 7 → 6 …… 直到 **N=0 = 全站永久 503**。

而在这条曲线上的每一个点,系统看起来都是**正常工作**的:

> **日志会一直打 `拒绝 inFlight=8/8`,与真实饱和长得一模一样。**

⚠️ **它与同批审阅的另一条是连着的**,ADR 把两条并排放在一起:
那条 WARN 里的**分子是同义反复** —— `tryAcquire()` 返 false 当且仅当那一刻可用名额为 0,
所以随后再读一次要么读回 `capacity`(**把「被拒了」重说一遍**),要么读回一个更小的数;
真正带信息的是**分母**。

> **两条是连着的:第一条是唯一能让第二条那个同义反复变成谎话的路径。**

名额一漏,`8/8` 就从「恒真」变成「在说一件假事」——
而那句假话,和真实饱和在日志上一个字都不差。

## 它为什么没被现有守护抓住

**因为已有的那条测试注入的是 `RuntimeException`。**

`permitIsReleasedWhenSubmitItselfFails` 注入一个抛 `RejectedExecutionException` 的
`Executor`,断言名额归还 —— **它是绿的,而且它测的东西是对的**。
缺的那一条要求注入一个 **`Error`**,而「往测试里注入一个 `Error`」
不是写这类用例时会自然想到的输入:`Error` 在日常心智里属于「JVM 要死了,谁还管名额」那一档 ——
而这条缺陷的全部要害恰恰是**JVM 并不会死**。

⚠️ **观测面在这一条上不构成保护,反而帮倒忙。**
准入拒绝有一条 WARN,它会照常打;但它的读数在「真的挤」和「名额被漏光」两种情形下**完全相同**。
**「我们有观测面」在这条缺陷上不是防线**——它是伪装。

## ⚠️ 它本可以怎样溜过去

**三层,一层比一层更像正常运行。**

**其一,触发点稀有。** 低流量下几乎不会走到起不出线程那一步;而这个项目的真实并发量级 ≈1。

**其二,漏还这个动作不留痕。** 它不是「执行了错误的分支」,是**该执行的那一行没被执行** ——
没有异常、没有日志、没有任何一处会变红。

**其三,终态看起来正好像这套机制在正常工作。** 全站 503 + `inFlight=8/8` 的日志,
读起来就是「负载太高,准入闸在挡」—— **而那正是我们刚装的这套东西该报告的东西**。
故障与机制正常工作长得一样,于是排查会从「是不是真的挤」开始,
而不是从「名额是不是漏了」开始。

## 是什么抓住了它

**审阅 —— 读 diff。** ADR 记的是「审阅抓到的两条,连在一起(Felix,2026-09-03)」。

不是测试、不是冒烟、不是探针。这一条的形状决定了自动化守护抓不到它:
**要发现它,必须把 catch 的那一行和上面几行 javadoc 放在一起读**,
然后问一句「`execute` 还能抛出什么」。

## 修法,以及它旁边那句注释才是真正的产出

**修法只有一行**:`catch (RuntimeException e)` → `catch (Throwable e)`(`6a62d95`)。

⚠️ **ADR 与代码没有记录别的候选** —— 这一条没有「更自然的那个修法」可比。
真正值钱的是修法**旁边**那句注释,它防的是**未来有人把它改回去**:

> ⚠️ **catch 接的是 `Throwable` 而不是 `RuntimeException` —— 这不是防御性宽泛,
> 而是那条唯一真正会发生的路径。**

`catch (Throwable)` 在多数代码库里是一个会被 code review 挡下来的写法,
而这里它是对的 —— **一行不解释自己的正确写法,和一个错误写法一样脆**:
下一个人会按通用直觉把它收窄回去,而那次收窄同样不会有任何东西变红。

## 留下了什么判据

新增的 `permitIsReleasedWhenSubmitThrowsError` 注入抛 `OutOfMemoryError` 的 `Executor`,
而它的**第二段断言**才是这条用例的重点 —— 注释逐字写着理由:

> 再来一次仍然是「占到名额 → 提交时抛」而不是「占不到名额」——漏还的话第二发会因为
> `tryAcquire` 失败而**静默返 false**(连异常都没有),那正是慢性失血看起来的样子。

**它断言的是「第二发仍然抛」,不是「返 false」。**
若只断言首发归还,一个漏还的实现在第二发上会**安静地**换一条路走,
而「安静」正是这条缺陷的指纹 —— **测试必须去看那个指纹,不能只看第一次的结果。**
配套的 `repeatedSubmitFailuresDoNotLeakPermits` 把它推到 N+1 次:**漏还一次这条就红。**

而 ADR 那句「两条是连着的」也留了下来 —— 它让下一个读日志的人知道:
`inFlight=N/N` 这个读数**在名额没漏的前提下**才是恒真的同义反复;
一旦前提破了,它就是那句最难被识破的假话。
