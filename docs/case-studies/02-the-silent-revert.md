# 闸 A · 一次没发生的静默撤销

> **拦截深度**:勘察(写码前)· **到过哪**:没写进代码 · **玩家可见**:否
>
> 出处:[ADR-022](../adr/ADR-022-turn-admission-and-rejection-semantics.md) §立字 11(「闸 A,刀 2 勘察时发现,2026-09-03」)。
> 本文只转写与索引,裁定真理源在 ADR。

## 现象

刀 2 的拒绝链要求「一种形状、三个状态」,于是它要给回合的 404 补一个结构化 body。
听起来是纯增量:原先是裸的 404,现在带上 `{error:{code, message}}`。

而前端的映射链是这样收口的(`h5GameApi.ts`,`statusFallback` 与它上面那行):

```ts
return { code: err?.code ?? fallback.code, message: err?.message ?? fallback.message };
```

**body 里的 `message` 会压过兜底表。**

于是:刀 2 一旦顺手给 404 的 body 带上一句 message,
**刀 1.5 花一整刀才定下来的那句文案会被无声换掉** ——
而那句话正是[上一篇](01-a-message-that-lied.md)里被真机冒烟**逐字证伪一次之后**才写出来的。

**⚠️ 而所有前端测试照常全绿。**

## 它为什么没被现有守护抓住

**因为两端各自都被测了,而契约本身没有被测。**

- 前端那侧有一整组用例覆盖优先级链(`body 带 error.code → code 与 message 都取 body`、
  `404 裸 body → session_not_found + 一句玩家做得到的话` …)。
  但它们喂给自己的桩是**自己写的 body** —— 没有任何一条知道「服务端某天会开始发 message」。
- 服务端那侧的用例断言的是自己发了什么,**不知道前端拿它做什么**。

两套测试**互不可见**。而这条契约恰恰是横跨它们的:
**「服务端发不发 message」与「前端那句文案还在不在」是同一件事的两端,却没有一个断言同时看得见两端。**

## ⚠️ 它本可以怎样溜过去

**它不是一个错误,是两条各自正确的规定的交集。**

刀 2 的实施步骤明写要补结构化 body;刀 1 的映射链明写 body 优先。
**任何一个人单独看两边,都会说「对」** —— 而只有把两条摆在一起,才看得出交集处发生了什么。

后果又恰好是**静默**的:文案换了,没有报错、没有日志、没有变红的测试。
玩家看到的仍是一条黄条,只是句子变了 ——
而**变回去的那句,正是被真机证伪过、且照它做会失败的那一句**。

换句话说:撤销它的代价,正好等于刀 1.5 那一整刀。

## 是什么抓住了它

**勘察。** 刀 2 开写前核对「那句立字写进 ADR 没有」时撞见的 —— 写码之前,
所以它**一行代码都没进过**。

这是这三篇里代价最小的一次拦截,而它靠的不是任何自动化守护,
是**动手前把两份口径摆在一起读**这个步骤本身。

## 修法,以及为什么不是更「自然」的那个修法

**修法:404 的 body 只发 code,不发 message。**

`GameController` 里那行旁边的注释逐字写着「只发 code,不发 message(ADR-022 闸 A 裁定)」,
而同一个文件里 `server_at_capacity` 的注释写的是「文案只有服务端知道 …… **与 404 相反**」。

⚠️ **关键在于它没有发明任何新机制。**
「`code` 与 `message` **各自独立兜底**」是**刀 1 就设计好的**(ADR §刀 1 步骤 2 逐字:
「故『code 取自 body、message 取自状态兜底』是允许的混合」),
**而且刀 1 当时就有一条测试钉着它** ——
`code 取自 body、message 缺失 → message 退状态兜底(两者各自独立兜底)`,
`git log -S` 实测由刀 1 的实现 commit `82fe06f` 引入。

**修法是用回一个已经存在、且已经被测试钉住的能力。**

⚠️ **更自然的那个修法被推翻了**:勘察时的初始建议是「**服务端也发同一句、加一条 lockstep 钉住两处**」
—— 那是本项目对付「两处不得漂移」的既有招式,用在这里看着顺理成章。
ADR 记着它被否决的理由(「刀 2 勘察时的初始建议,Felix 推翻」):

> 它会引入**本仓第一条 server 测试读 `web/` 源文件**的架构耦合方向。既有跨目录 lockstep
> …… 守的都是**运行时真依赖**;而那条要守的是**一份没有任何运行时关系的、拷贝的拷贝**。
> **为一个字符串开一道新的架构耦合方向,不划算。**

## 留下了什么判据

它留下的不是一条测试,是**一条规则**(立字 11):

> **状态码本身就能说清的情形,文案归前端兜底表;只有服务端知道的细节,文案归服务端。**

- **404**「这个档没了」—— 状态就能知道,且那句话引用的是**前端控件名**「返回」,
  服务端没有理由知道那个按钮叫什么 → body **只带 code**;
- **`server_at_capacity`**「此刻挤 / 过几秒」、**`quota_exceeded`**(知道具体额度)、
  **`illegal_action`**(知道是哪个动作)—— 只有服务端知道 → **服务端发文案**。

⚠️ 于是那两个方向相反的决定**不是两个特例,是同一条规则的两侧**;
「一种形状、三个状态」也没有因此破 —— 形状仍是 `{error:{code, message?}}`,
`message` 何时出现由本条规则决定,**写进立字它就是契约,不是特例**。

守护落在两侧,各守自己:

- **服务端侧**:404 响应 `doesNotContainKey("message")`,外加一条 MockMvc 用例;
- **前端侧**:`404 + 只有 code 的 body → code 取 body、message 退兜底(刀 2 的真实形状)`。

⚠️ **一处如实记**:闸 A 最初写的守护期望是「给服务端 404 加 message → **前端**那条用例必须变红」——
**在构造上做不到**,原因正是上面那条(两套测试互不可见)。
真实分工是**两条各守一侧,合起来才是这道闸的守护本体** ——
**没有任何单条断言能覆盖一条横跨两个测试套件的契约。**
